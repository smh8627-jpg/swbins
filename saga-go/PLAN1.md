# SAGA-GO Godot 4 전환 및 대규모 리뉴얼 작업지시서

## 0. 최우선 원칙

현재 프로젝트:

https://smh8627-jpg.github.io/swbins/saga-go/

이 프로젝트를 참고하여 기존 게임의 핵심 게임플레이 아이디어와 콘텐츠 의도는 유지하되, **Godot 4 기반의 모바일 3D 게임으로 재구축한다.**

### 절대 원칙

1. 기존 HTML/CSS/JavaScript를 그대로 Godot에 억지로 이식하지 않는다.
2. Godot 4의 Scene / Node / Resource / GDScript 구조로 재설계한다.
3. 기존 프로젝트의 좋은 기능과 게임플레이는 분석 후 유지한다.
4. 그래픽 품질이 낮은 기존 구현을 그대로 복사하지 않는다.
5. 가능하면 실제 3D GLB/GLTF 에셋을 사용한다.
6. 모바일 성능을 최우선으로 고려한다.
7. 세로 모드와 가로 모드를 모두 지원한다.
8. Android/iOS를 주요 타깃으로 설계한다.
9. 웹 빌드는 테스트 및 데모용으로만 고려한다.
10. 구현 전에 반드시 현재 프로젝트를 분석한다.

# 4. 엔진 설정

Godot 4 기준으로 작업한다.

모바일 3D 게임이므로 기본 렌더러는:

```text
Mobile Renderer
```

를 우선 사용한다.

저사양 기기 대응을 위해 Compatibility Renderer로 전환 가능한 구조도 고려한다.

Forward+를 기본으로 사용하여 모바일 성능을 희생하지 않는다.

# 6. 3D 그래픽 품질 목표

현재 프로젝트의 가장 큰 문제점 중 하나가 낮은 그래픽 완성도이므로 다음을 적용한다.

## 반드시 개선

### 플레이어

실제 3D 캐릭터 모델 사용.

가능하면:

- GLB
- GLTF

사용.

Godot는 glTF 2.0 및 GLB를 공식적으로 지원하므로 기본 3D 에셋 포맷으로 사용한다.

---

### 적

적마다 외형 차이를 만든다.

예:

- 슬라임
- 늑대
- 고블린
- 오크
- 해골
- 마법 몬스터
- 거대 몬스터

단순히 색깔만 변경한 동일 모델을 반복하지 않는다.

---

### 환경

맵에 다음 요소를 적극적으로 배치한다.

- 나무
- 바위
- 풀
- 꽃
- 버섯
- 언덕
- 절벽
- 다리
- 폐허
- 캠프
- 건물
- 상자
- 횃불
- 제단
- 동굴 입구
- 폭포
- 강
- 작은 연못

목표는:

"빈 평면 위에 캐릭터와 적만 존재하는 게임"

이 되지 않도록 하는 것이다.

# 7. GLB 에셋 정책

3D 모델은 가능한 한 실제 에셋을 사용한다.

우선순위:

1. 무료/오픈 라이선스 에셋
2. 상업적 사용이 가능한 에셋
3. 직접 제작한 에셋
4. 임시 Primitive

Primitive는 프로토타입에서만 사용한다.

최종 게임에서는:

```text
Cube
Sphere
Cylinder
```

만으로 캐릭터와 환경을 구성하지 않는다.

- 카메라 흔들림

# 23. 성능 최적화

모바일 게임이므로 성능을 처음부터 고려한다.

### 금지

불필요한:

- 고해상도 텍스처
- 과도한 그림자
- 수많은 실시간 광원
- 과도한 파티클
- 지나치게 높은 폴리곤
- 매 프레임 무거운 코드

사용 금지.

---

# 24. 에셋 최적화

모바일에서는 텍스처 크기를 관리한다.

가능하면:

```text
512
1024
2048
```

범위를 우선 사용한다.

4K 텍스처는 꼭 필요한 경우만 사용한다.

Godot 문서에서도 모바일 GPU는 일반적으로 4096×4096 수준의 텍스처 제한을 고려해야 하므로 무조건 고해상도 텍스처를 사용하는 방식은 피한다.

---

# 25. 오브젝트 최적화

필드에 오브젝트가 많아질 경우:

- LOD
- Culling
- Visibility Range
- Object Pooling

등을 고려한다.

특히 적은:

```text
Enemy Pool
```

구조를 사용하여 불필요한 instantiate/free 반복을 줄인다.

# 29. 코드 품질

GDScript는 명확하게 작성한다.

함수는 작게 유지한다.

한 함수가 너무 많은 역할을 하지 않도록 한다.

중복 코드를 만들지 않는다.

공통 기능은 별도 클래스로 분리한다.

---

# 30. 기존 게임의 기능 보존

기존 saga-go를 분석한 후 기존 게임에서 유효한 기능은 유지한다.

하지만 다음은 그대로 가져오지 않는다.

- 낮은 품질의 그래픽
- 임시 UI
- 복잡하게 얽힌 JS 구조
- 불필요한 코드
- 브라우저 전용 구현
- 중복 데이터

즉:

```text
Gameplay = 참고/계승
Architecture = Godot로 재설계
Graphics = 대폭 개선
UI = 재설계
Performance = 모바일 기준 재설계
```

# 35. GitHub / 기존 웹 프로젝트와 분리

기존 프로젝트를 바로 파괴하지 않는다.

기존:

```text
saga-go
```

는 백업/참고용으로 유지한다.

새로운 Godot 프로젝트:

```text
saga-go-godot
```

로 별도 구축한다.

기존 프로젝트에서 필요한 자료만 가져온다.

# 36. Claude Code 작업 방식

Claude Code는 매 단계마다 다음 형식으로 작업한다.

```text
[현재 상태]

[이번 목표]

[구현]

[검증]

[다음 단계]
```

불필요한 장황한 설명은 하지 않는다.

# 39. 절대 금지

다음 행동은 하지 않는다.

- 기존 파일 전체를 무조건 읽기
- 같은 파일 반복 읽기
- 필요 없는 리팩터링
- 기능과 관계없는 코드 수정
- 모든 시스템을 한 번에 구현
- 설명만 길게 출력
- 테스트하지 않고 다음 단계 진행
- 모바일 성능을 마지막에만 고려
- Placeholder 그래픽을 최종 그래픽으로 사용

# Claude Code 첫 실행 지시

위 요구사항을 모두 읽은 후 바로 대규모 코드를 작성하지 않는다.

먼저 현재 saga-go 프로젝트를 분석한다.

분석 후 다음만 출력한다.

1. 현재 게임 구조
2. 유지할 기능
3. 버릴 기능
4. Godot에서 새로 설계할 시스템
5. 필요한 3D 에셋 종류
6. 예상 Godot 폴더 구조
7. 1단계 구현 계획

그리고 확인이 끝나면 **PHASE 1부터 최소한의 파일만 생성하여 시작한다.**

토큰 사용량을 항상 최소화한다.

동일한 정보를 반복해서 설명하지 않는다.
