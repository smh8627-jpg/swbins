# VERTICAL_SLICE_FOREST

PLAN.md 39장 순서(Core → Vertical Slice(GO) → DUNGEON → **FOREST** → STORY →
REALM)의 세 번째 칸. GO·DUNGEON Vertical Slice는 코드로는 완료됐다(DUNGEON은
2026-09-12에 "제외" 목록 1~7번 전부 끝남, GUI 실기 확인·Vertical Slice 승인
게이트는 아직 대기 중). **사용자가 "다음 판 계획이나 살펴봐"로 FOREST 설계를
먼저 들여다보라고 지시했고, 이어서 "구면 투영부터 정하자"로 이 문서의 첫
결정을 지시했다(2026-09-12).** DUNGEON의 승인 게이트를 반드시 먼저 통과해야
FOREST 설계에 손을 댈 수 있는 건 아니다 — PLAN.md 39장은 "구현 착수 순서"고,
이 문서는 아직 설계(Phase 2) 단계라 병행해도 무방하다.

LEGACY_FEATURE_AUDIT.md "SAGA FOREST" 절의 KEEP/REWORK/MERGE/DROP 분류를
그대로 따른다 — DROP은 없다("FOREST는 PLAN.md/README와 실제 코드가 가장
일치하는 판이라 버릴 게 적다"). 이 문서는 REWORK 하나(렌더링, 특히 "구면
투영")부터 순서대로 설계 결정을 쌓아 간다 — 아직 다 안 채워졌다, 결정될
때마다 이어서 적는다.

## 1. 구면 투영 — 렌더링 방식 결정 (2026-09-12)

### 원작(웹판)이 하던 일

`saga-forest/js/village-view.js`의 `project(wx, wy)`/`unproject(sx, sy)` —
**순수 2D 캔버스 화면 왜곡**이다. 마을의 실제 좌표(`village.js`의 타일
좌표)는 완전히 평면 그리드고, 화면에 그릴 때만 이 두 함수를 거쳐 굽어
보이게 만든다(판정은 항상 평면 좌표로 하고, `pointAt()`이 화면 클릭을
다시 `unproject`로 되짚어 평면 좌표로 돌려놓는다).

```text
project(wx, wy):
  a  = clamp(dy/R, ..1.2)                    # 세로(북남) 각도 비슷한 값
  s  = clamp(1/(1 - a*0.40), 0.42, 1.55)      # 세로 위치에 따른 가로 확대율
  sx = CX + (wx-cam.x) * ZOOM * s
  d  = sx - CX
  sy = CY + R*ZOOM*TILT*sin(a) + d*d*BEND     # 세로는 sin(a) 기준, 거기에
                                               # 가로 거리의 제곱(BEND)을 더해 휜다
```

세로(`sin(a)`)와 가로(`d²·BEND`)가 **비등방**으로 따로 처리된다 — 오블리크
2D 카메라가 만든 근사식이지, 지켜야 할 규칙 자체는 아니다.

### 결정 — 정점 셰이더, 등방(원형) 포물면

**진짜로 휜 지형(구 지오메트리)이 아니라 순수 시각 효과로 간다.** 세계
좌표·걷기·타일 판정은 GDScript에서 계속 평면 그리드로 계산한다 — 웹의
"project/unproject는 그림만, village.js 판정은 평면 그대로"와 정확히 같은
경계다.

3D는 실제 카메라 원근이 이미 "멀수록 낮아 보이는" 효과를 주므로, 웹의
비등방 공식을 그대로 옮기지 않고 **중심(플레이어) 기준 원형 포물면** 하나로
재설계했다 — 사방 어디를 봐도 같은 규칙으로 휘어야 이음매가 안 생긴다
("그릇 안에 서 있다"는 느낌).

```glsl
// saga_core/shaders/world_curve.gdshaderinc
vertex_local.y -= dot(world_xz - saga_world_curve_center.xz, ...) * curve_amount
```

- **공용 include로 뽑았다**(`saga_core/shaders/world_curve.gdshaderinc`) —
  다른 트랙·다른 게임이 같은 개념을 나중에 쓰고 싶어지면 재사용할 수 있게
  (PLAN.md 6장 공용화 경계와 같은 자리), 지금은 FOREST만 쓴다.
- **전제 — Y축 회전(요)만 쓰는 오브젝트에만 유효하다.** 이 프로젝트의 월드
  오브젝트는 전부 Y축 회전만 쓴다(GO/DUNGEON에 피치·롤 없음) — Y축 회전은
  로컬 Y 성분을 안 바꾸므로, 월드 XZ로 굽힘량만 구해 로컬 `VERTEX.y`에서
  바로 빼는 것으로 충분하고 모델 역행렬이 필요 없다. 나중에 피치·롤 있는
  오브젝트에 쓸 일이 생기면 이 전제부터 다시 볼 것.
- **중심은 플레이어 월드 좌표**(웹의 `cam.x/cam.y`도 결국 플레이어를 따라가는
  카메라 중심이라 같은 뜻) — 매 프레임(또는 이동할 때) `RenderingServer.
  global_shader_parameter_set("saga_world_curve_center", player.global_position)`
  로 갱신한다. 이 값을 쓰는 모든 머티리얼(지형·건물·초목·NPC·플레이어 자신)이
  **같은 global uniform 하나**를 봐야 한다 — 땅만 휘고 나무는 안 휘면 나무가
  공중에 뜬 것처럼 보인다.
- **집 안·동굴 안은 이 include를 아예 안 쓰는 머티리얼로 남긴다**(루트
  CLAUDE.md "구면 투영을 평평한 탑다운으로 되돌리지 않는다 — 집 안만은
  일부러 안 휜다") — 새 예외 처리가 필요 없다, 그냥 실내 전용 씬/머티리얼이
  이 셰이더를 안 물리면 된다.
- `curve_amount` — **원작에 없는 값, 직접 정함**(웹은 화면 픽셀 단위
  상수라 미터 단위로 그대로 못 옮긴다). 임시로 0.004: 중심에서 10m 떨어지면
  0.4m, 20m 떨어지면 1.6m 가라앉는다 — 마을 규모(30×20 칸)에 맞춰 나중에
  실기로 튜닝한다. 셰이더 상수로 안 박고 머티리얼별 uniform으로 노출해 뒀다.

### 검증 (헤드리스, 2026-09-12)

임시 스크립트(`_curve_test.gd`+`_curve_test.gdshader`, 검증 뒤 삭제,
저장소에 안 남음)로 확인:

- **셰이더 컴파일 확인** — `#include` 로 `world_curve.gdshaderinc`를 물고,
  `load()`로 정상 로드됨(문법 오류 없음).
- **공식 검산(CPU 재현)** — offset (10,0)→0.4m, (20,0)→1.6m, (7,7)→0.392m로
  기대한 크기와 부호(파낸다=낮아진다)가 맞음.
- **global uniform 왕복은 헤드리스에서 확인 불가로 판명** —
  `RenderingServer.global_shader_parameter_add()`로 등록하고 `set`/`get`을
  해 봐도 `--headless`(더미 렌더러)에서는 `get`이 계속 `null`을 돌려준다.
  API 사용법이 틀린 게 아니라(공식 문서의 표준 방식 그대로) **헤드리스
  더미 렌더러가 이 기능 자체를 stub만 해 둔 것으로 보인다** — 실제 반영
  여부는 에디터/실기로만 확인된다. 에디터를 한 번 `--editor --quit`로
  띄운 것만으로는 `project.godot`에 `[shader_globals]` 항목이 자동으로
  안 생기는 것도 같이 확인했다(그 셰이더가 실제 씬에서 쓰여야 에디터가
  감지하는 것으로 보인다) — 그러니 **런타임에 `global_shader_parameter_add()`로
  직접 등록하는 코드가 필요하다**, project.godot 자동 등록에 기대면 안 됨.
- **GUI 실기 확인은 아직 안 함** — 실제로 화면에서 지형이 그릇처럼
  휘어 보이는지, `curve_amount=0.004`가 적당한지, 중심을 벗어난 오브젝트가
  자연스럽게 가라앉는지. FOREST 씬이 아직 없어(Phase 1 미착수) 지금은
  확인할 실제 지형도 없다 — 월드가 서면 그때 같이 몰아서 본다(루트
  CLAUDE.md 실기 확인 방침).

## 2. 월드 스케일 — 결정 (2026-09-12)

### 원작(웹판)이 쓰는 값

`saga-forest/js/village.js`:

```js
var W = 30, H = 20;   // 마을 크기 (타일)
var TILE = 40;        // 한 타일 = 몇 단위 (그림 크기와 무관한 논리값)
var REACH = 46;       // 사물에 손이 닿는 거리
```

`TILE=40`은 화면 픽셀과 무관한 순수 논리 단위다 — 중요한 건 절대값이
아니라 **비율**: `REACH/TILE = 46/40 = 1.15`, 즉 "손이 닿는 거리"는 한
타일보다 살짝 더 넓다(인접 타일의 사물까지 닿는다는 뜻).

### 결정 — 1타일 = 3.0m, 30×20 마을 = 90m×60m

GO(48유닛/타일, 7×7 **성긴** 매크로 칸에 랜드마크를 드문드문 배치)·
DUNGEON(방 12m, 사람 한둘 지날 통로)과 FOREST는 격이 다르다 — FOREST의
30×20은 **칸 하나하나가 전부 밟는 땅**이다(나무 한 그루·꽃 한 송이·집
모서리가 실제로 한 칸씩 차지, 원작 동물의숲 자체가 그렇다). 그래서 GO의
48m/칸을 그대로 가져오면 마을이 1440×960m로 터무니없이 커진다 — FOREST
고유 값이 필요했다.

- **TILE_SIZE = 3.0m.** 이미 확인된 자산 실측치와 맞아떨어진다 —
  `docs/ASSET_GUIDE.md`의 `tree_oak.glb`(GO가 ×4.5로 쓰는 그 나무)는 실제
  크기 0.64×1.23×0.74m를 ×4.5 하면 캐노피 폭 ≈2.9m — **나무 한 그루가
  타일 하나에 딱 들어맞는다**(원작처럼 "타일 = 사물 하나"가 자연스럽게
  성립). 새 자산을 안 구하고 GO가 이미 검증해 둔 나무·바위 GLB를 그대로
  재사용할 수 있다는 뜻이기도 하다.
- **REACH = 1.15 × TILE_SIZE ≈ 3.45m**(원작 비율 그대로) — DUNGEON의
  근접 사거리(2.4m)보다 조금 넓다, 전투가 아니라 "다가가서 줍는다/
  대화한다"용이라 그 정도가 자연스럽다.
- **마을 전체 = 90m × 60m.** 사람 걷는 속도(대략 3~4m/s, GO/DUNGEON의
  이동 속도 상수와 같은 자릿수)로 한쪽 끝에서 반대쪽까지 30초 안팎 —
  "그냥 돌아다녀도 재미있다"는 느긋한 산책 범위지, GO식 광활한 탐험
  범위가 아니다. 원작(동물의숲)의 "다닥다닥 붙은 아늑한 마을" 밀도에
  더 가깝다.
- **`curve_amount`(1절)는 이미 이 스케일과 어긋나지 않는다** — 10m·20m
  예시가 그대로 3.3~6.6칸 범위라 재조정이 급하지 않다. 실제 마을이 서면
  같이 다시 본다(1절 "GUI 실기 확인은 아직 안 함" 그대로 유지).
- **아직 안 정한 것** — 이 상수들을 실제로 담을 파일 이름(`games/
  saga_forest/data/village_map.gd`류, GO의 `test_map.gd`와 같은 자리)은
  Phase 1(폴더 생성)에서 정한다. 지금은 숫자만 정했다.

## 3. 카메라 — 결정 (2026-09-12)

### 원작(웹판)이 하던 일

처음엔 "탐험이 핵심이니 GO의 회전 카메라 쪽이 아닐까" 짐작했는데(2절
초안), **실제로 코드를 보니 원작이 이미 고정 카메라였다.**
`village-view.js`:

```js
var R = 520, TILT = 0.66, BEND = 0.000155, ZOOM = 1;   // 셋 다 상수 — 안 바뀐다
cam.x = p.x; cam.y = p.y;                               // 카메라는 플레이어 위치만 따라간다
```

회전 입력(드래그로 각도 바꾸기)도, 줌 입력(휠/핀치)도 **어디에도 없다.**
플레이어가 어디로 걷든 화면이 보는 각도는 늘 같다 — DUNGEON이 "디아블로처럼
화면 고정"을 사용자 요청으로 **새로 결정**한 것과 달리, FOREST는 원작 자체가
처음부터 고정 카메라였다.

### 결정 — DUNGEON의 고정 카메라 구조를 그대로 재사용

**GO의 회전 카메라(`camera_rig.gd`)가 아니라 DUNGEON의 `dungeon_camera_rig.gd`
쪽을 그대로 쓴다.** 이유는 취향이 아니라 원작이 이미 그렇게 만들어져 있어서다.
게다가 `dungeon_camera_rig.gd`는 뜯어보니 DUNGEON 전용 로직이 하나도 없다 —
`pitch_deg`·`spring_length` 두 값을 한 번 고정하는 것뿐인 순수 범용
컴포넌트라, **새 스크립트를 안 짜고 크로스게임으로 그대로 가져다 쓴다**
(GO의 `choice_prompt.gd`를 DUNGEON이 그대로 가져다 쓰는 것과 같은 경계,
PLAN.md 32·33장 "동일한 코드를 복사하지 않는다").

```text
Player(CharacterBody3D, games/saga_go/player/player.gd 재사용)
├── Visual(character-a.glb) — 이동 방향으로 이 노드만 도는 것도 GO/DUNGEON과 동일
├── CameraRig(Node3D, dungeon_camera_rig.gd 재사용)
│   └── SpringArm3D(collision_mask=1 — 벽에 안 파고들게, 그대로)
│       └── Camera3D
```

- **`Player` 루트는 회전하지 않는다**(GO player.gd가 `Visual` 자식만 돌린다) —
  그래서 `CameraRig`가 `Player`의 자식이어도 카메라의 요(yaw)는 절대 안
  바뀐다. 이게 진짜 "고정 카메라"의 핵심이다(화면상 방향이 고정, 캐릭터만
  제자리에서 돈다) — DUNGEON에서 이미 검증된 그 구조 그대로.
- **`pitch_deg = 62.0`**(DUNGEON의 55°보다 조금 더 위에서 내려다본다) —
  원작 없음, 직접 정함. `TILT=0.66` 같은 웹 상수는 오블리크 2D 캔버스
  수식용이라 각도로 그대로 환산할 수 없다 — 대신 장르 기준으로 판단했다:
  동물의숲류는 액션 게임보다 더 위에서 내려다봐 마당·화단이 잘 보여야
  한다(DUNGEON은 근접 전투가 핵심이라 55°로 더 낮게 잡았던 것과 반대
  이유).
- **`spring_length = 14.0`**(DUNGEON의 12m보다 살짝 멂) — 2절에서 정한
  90×60m 열린 마을을 걸을 때 주변이 좀 더 보이게. 두 값 다 실기로 튜닝할
  자리(다른 첫 상수들과 같은 경계).
- **줌·회전 입력 없음** — 원작 그대로(위 참고), DUNGEON과도 같은 결정.
- **곡률(1절) 보정은 필요 없다는 것으로 판명** — 처음엔 "카메라도 휜
  지면에 맞춰 보정이 필요할 수 있다"고 적어 뒀었는데, 따져 보니 아니었다.
  구면 투영은 **정점 셰이더**(순수 렌더링 트릭)라 카메라의 실제 Transform·
  SpringArm3D의 충돌 판정(둘 다 평면 콜리전 기준)에는 전혀 안 걸린다 —
  카메라는 곡률의 존재를 몰라도 된다.
- 이동 방향 계산(`player.gd::_world_direction()`)은 이미 `camera_rig`가
  회전하든 말든 그 자리에서 basis를 읽어 동작하게 짜여 있어(GO/DUNGEON
  공용) FOREST도 손댈 게 없다 — 카메라가 안 도니 조작감은 자연히 "위쪽이
  항상 같은 방향"인 고정 방향 이동이 된다(DUNGEON과 동일한 조작 감각).

### 나중에 볼 것(사소한 정리, 지금 안 함)

`dungeon_camera_rig.gd`가 이제 DUNGEON·FOREST 둘 다 쓰는 순수 범용

## 4. 첫 콘텐츠 루프 — 결정 (2026-09-12)

### 원작 KEEP 목록과 핵심 루프

LEGACY_FEATURE_AUDIT.md: **"핵심 루프 — 걷는다 → 채집한다 → 나눈다(주민과)."**
KEEP은 크다 — 구면 투영·채집(나무/소나무/바위/꽃 하루1회, 낚시 무제한)·
주민 5명+부탁+선물+편지·곤충/화석/조개 도감·박물관·순무 시세·벽지/장판·
꽃 교배·계절행사 8일·옷. DUNGEON이 "가장 시스템이 복잡한 판"으로
꼽혔었지만 FOREST도 KEEP이 그만큼 많다 — DUNGEON 이상으로 강하게 잘라야
한다(3장 Vertical Slice First, "재미가 확인된 후 콘텐츠를 확장한다").

참고로 `data-village.js`의 `NPCS`(숲지기·낚시꾼·상인·탐험가·약초꾼·
나그네)는 **역할 이름**이지 실존 인물이 아니다 — GO/DUNGEON의 "등용"
대상(`saga_core Characters`, 역사 인물 오마주)과 처음부터 다른 결이다.
FOREST의 정체성은 인물 로스터가 아니라 구면 투영+채집+생활 루프 쪽에
있다는 뜻이라, 아래 5절의 "몬스터·퓨전" 질문과는 별개 축이다.

### 결정 — 포함

```text
마을 지형 하나(좌표 해시 고정 배치, 2절 스케일 90×60m) — 잔디·흙길·
  나무 몇 그루(GO의 tree_oak.glb 재사용)만, 지형 다양성(꽃밭·어둑숲 등
  바이옴)은 이번엔 안 만든다
플레이어 이동(player.gd 재사용) + 고정 카메라(3절)
채집 동사 하나만: 나무 흔들기 → 과일 하나 획득(data-village.js GATHER.tree
  그대로, "reset:1"(하루 1회)은 이번엔 무시 — 무제한으로 흔들 수 있다,
  하루/시간 시스템 자체가 이번 슬라이스 밖이라)
주민 1명(NPCS 중 하나, 이름 그대로) + 말 걸기(대사만 — 부탁/선물/편지는
  제외, GO 첫 슬라이스의 NPC 범위와 같은 경계)
집 하나 + 들어가기/나가기 — **구면 투영이 실제로 꺼졌다 켜지는 것**을
  증명하는 자리(1절 "집 안만 안 휜다"의 첫 실증)
저장/불러오기(위치+채집한 과일 개수 정도, GO/DUNGEON과 같은 최소 범위)
```

### 결정 — 제외 (다음 슬라이스로 미룸)

```text
소나무/바위/꽃 등 나무 이외 채집 대상, 하루 1회 리셋(day 시스템 자체)
낚시(별도 미니게임)
주민 5명 전체 + 부탁·선물·편지 (첫 슬라이스는 1명, 대사만)
곤충/화석/조개 채집도감, 박물관(사고)
순무 시세(카부) — 경제 시스템
벽지/장판, 꽃 교배, 계절행사 8일, 옷(침선방)
바이옴 지형 다양성(꽃밭·어둑숲·버섯숲·바위 지대)
몬스터·퓨전 콘텐츠(5절 — 그 자체가 아직 별개로 미정)
```

### 완료 조건

```text
게임 실행 → 3D 마을(구면 투영) 진입 → 걷는다 → 나무를 흔들어 과일을
줍는다 → 주민에게 말을 건다 → 집 안으로 들어간다(평평해짐 확인) →
다시 나온다(다시 휘어짐 확인) → 저장한다 → 다시 켜서 이어진다
```

GO의 12단계·DUNGEON의 8단계와 같은 자리 — 이 일곱 단계가 "그냥 돌아다녀도
재미있는가"(LEGACY_FEATURE_AUDIT.md의 핵심 루프 문장)를 스스로 답할 수
있으면 성공이다. **"집 안 들어가기"를 일부러 넣은 이유** — 구면 투영은
이번 문서 전체에서 아직 실기로 한 번도 확인 못 한 신규 메커니즘이라, 첫
슬라이스 완료 조건 안에 "커브가 실제로 꺼졌다 켜지는" 장면을 넣어 두면
그 실기 확인이 뒤로 밀리지 않는다.

## 5. 몬스터·퓨전 자유 — 결정 (2026-09-12)

### 결정 — saga-godot 트랙에도 적용한다

**사용자가 "몬스터·퓨전 자유가 saga-godot 트랙에도 적용"으로 확정.** 2026-09-10
웹판 saga-forest 한정으로 나왔던 메모("동물의숲 완전 모방 아님, 괴물·다른
캐릭터·시대혼합 다 허용")를 saga-godot FOREST 트랙에도 그대로 확장한다 —
5절 마지막 미정 항목이었던 질문이 이걸로 풀렸다.

- PLAN.md 5장의 "역사 인물로 노는" 정체성 문구와 충돌하는 것으로 보였지만,
  4절에서 이미 확인했듯 **FOREST의 주민(NPCS)은 애초에 역사 인물이 아니라
  역할 이름**(숲지기·낚시꾼·상인 등)이다 — 그 정체성 문구는 GO/DUNGEON의
  "등용"(saga_core Characters, 역사 인물 오마주) 로스터에 관한 것이지
  FOREST에는 처음부터 안 걸리는 축이었다. 그러니 이 결정은 "주민을 역사
  인물로 바꾼다"가 아니라 **"몬스터·다른 시대 요소를 넣어도 된다"**는
  뜻이고, PLAN.md 5장과 실제로 충돌하지 않는다.
- 이 결정은 **자유를 준 것이지 이번 Vertical Slice에 당장 넣으라는 뜻은
  아니다** — 4절 "결정 — 제외" 목록의 "몬스터·퓨전 콘텐츠"는 그대로 유효,
  첫 슬라이스는 여전히 걷기/채집/대화/저장까지만이다. 몬스터·퓨전은 39·51장
  순서대로 **Vertical Slice 승인 이후 콘텐츠 확장 단계**에서 쓸 수 있는
  선택지가 하나 늘었다는 뜻으로 남겨 둔다.
- 이걸로 FOREST 설계(Phase 2, 이 문서 1~5절)가 전부 끝났다. 다음은 GO/DUNGEON이
  밟은 순서(Phase 1 프로젝트 폴더 생성 → Phase 3 3D World 구현 착수)로
  넘어가는 게 자연스럽다 — 단, 착수 여부는 사용자에게 확인받는다(DUNGEON의
  GUI 승인 게이트도 아직 대기 중인 것과는 별개 사안).
