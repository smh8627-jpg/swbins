# LEGACY_FEATURE_AUDIT

master.md 4장의 KEEP/REWORK/MERGE/DROP 분류. saga-go/dungeon/forest/story/realm의
`PLAN.md`(웹·Three.js 전환) · `PLAN1.md`(Godot 전환, 미착수) · `PLAN2.md`(Unity 전환,

## 0. 가장 먼저 알아야 할 것 — master.md가 놓친 정체성

master.md 5장("5개 게임의 역할 재정의")은 다섯 판을 전부 "고블린/오크/해골을 잡는
일반 판타지 RPG"처럼 재정의했다. **틀렸다.** 이 저장소의 진짜 정체성은 루트
`CLAUDE.md` 1행에 있다 — **"역사 인물로 노는 웹 게임 다섯 판"**. 다섯 판 다
`data.js`(역사 인물 데이터, 삼국지·한국사·유럽사 실존 인물)를 공유하고, 각자
포켓몬GO/디아블로/동물의숲/메이플스토리/코에이삼국지의 **틀만** 빌려 그 인물들을
등용·성장시킨다. 몬스터가 아니라 **인물**이 이 게임들의 핵심 재화다. saga-godot을
설계할 때 이 축을 빠뜨리면 "장르만 다른 다섯 개의 똑같은 판타지 RPG"가 된다 —
그건 이 프로젝트가 아니다.

또한 다섯 폴더 다 **이미 자체적으로 3D 전환을 설계/착수했다** — 다만 Godot이
아니라 **Three.js(웹)** 로. `PLAN.md`가 그 실행 중인 계획이고, `PLAN1.md`(Godot)·
`PLAN2.md`(Unity)는 같은 시기에 같이 작성됐지만 **한 줄도 실행되지 않은 대안
설계도**다(예: `saga-go-godot/` 폴더는 실존하지 않는다). master.md가 최종적으로
Godot을 선택했으므로, PLAN1.md가 가장 가까운 출발점이지만 — PLAN1.md 다섯 벌은
전부 "고블린·늑대·해골"류 제네릭 몬스터 RPG로 쓰여 있어 실제 이 게임들의 정체성
(역사 인물, 원작 시스템을 상표 회피해 재해석한 이름들)을 전혀 반영하지 않는다.
**PLAN1.md는 구조(폴더·Phase 순서·Godot 노드 패턴)만 KEEP하고, 콘텐츠는 각
게임의 실제 README에서 다시 뽑아야 한다.**

## 1. 공용 규칙 — 절대 어기면 안 되는 것 (전부 KEEP, 무조건)

- **세이브 키 ≠ 폴더 이름.** `deungyong-go`·`yeoksa-dungeon`·`yeoksa-village`·
  `yeoksa-side`·`saga-realm`. Godot으로 옮겨도 저장 슬롯 개념(user:// 파일명 등)에
  이 이름을 그대로 쓴다 — 폴더 이름(`saga_go` 등)에 맞추면 기존 진행이 아무 의미
  없어진다(맞출 진행이 saga-godot엔 없지만, 이식 스크립트를 짤 때 이 매핑을 기억해야 함)
- **다섯 벌 복사 구조 — 웹판(saga-go 등)에서는 그대로 유지.** `data.js`(인물)·
  `sprite.js`·`core.js`·`hero.js`는 기존 다섯 웹 프로젝트에서 계속 각자 한 벌씩
  갖는다(루트 CLAUDE.md 규칙, 안 바뀜). **단 saga-godot(신규 Godot 프로젝트)에서는
  사용자 결정으로 인물 데이터를 공유한다** — `saga_core/data/characters/`에 인물
  데이터를 한 벌만 두고 다섯 게임이 참조한다(2026-08-31 결정, 아래 "인물 데이터
  공유 결정" 절 참고). `sprite.js`(그림 규칙)는 게임마다 양식이 다르므로
  (diablo/maple/storyize 등) 계속 게임별로 분리한다 — 공유 대상은 **데이터**뿐이지
  그림 스타일이 아니다
- **도감 인물 id 불변.** 표시 이름은 원작 상표 회피로 바꾼 적 있지만(`b0f6cde`)
  id는 안 바꾼다. Godot으로 옮겨도 이 규칙은 그대로다
- **원작 에셋을 가져오지 않는다.** 그림 문법만 따르고 그림은 코드/CC0 에셋으로.
  이미 다섯 판 다 Quaternius 등 CC0 GLB로 실제 3D 전환 중이라 master.md 8장
  ("실제 3D 에셋 기반")과 자연스럽게 맞다 — 이 원칙만 지키면 REWORK 불필요, KEEP
- **원작 시스템을 그대로 베끼지 않고 한자어로 재해석한 이름들.** 등용(원작 뽑기) ·
  은사(디아블로 랜덤버프) · 무예(스킬트리) · 투장(세트아이템) · 연단(호라드릭큐브) ·
  행상/투전(상점/도박) · 부문/부문어(룬/룬워드) · 사명(퀘스트) · 학당(문답) 등.
  이 이름들은 **KEEP** — 상표 회피와 이 프로젝트의 톤을 동시에 담당한다
- **진단 습관.** mulberry32 고정 씨앗(20260824) · `_test.html` RESULT n/n · 3회
  동일 확인 · 시각 의존 축(전투·날씨)은 진단에서 강제 고정. Godot으로 가도
  같은 정신(결정적 시드, 헤드리스 회귀 테스트)을 `--headless --quit` 기반으로
  다시 세워야 한다 — REWORK(도구는 바뀌지만 원칙은 KEEP)

## 2. 게임별 감사

### SAGA GO (포켓몬GO 틀)

**핵심 루프**: 걷는다(보급) → 만난다(NPC·짐승·사건) → 등용/포획 → 부대 성장.
지도 기반이 아니라(GPS 없음) **손으로 그린 소규모 지역**(1008m 사방) 위를 걷는
쪽으로 이미 웹 3D 전환에서 방향이 잡혔다.

| 분류 | 내용 |
|---|---|
| KEEP | 등용(역사 인물 포획) · 소문/사건 시스템(열 가지 사건, 걸은 거리 기반) · 발견 도감(지역·사람·생물·사건·역사 5갈래) · NPC 일과(시각의 순수 함수) · 짐승 생태(사슴/늑대/까치/잉어/소, 잡히지 않음) · 계절(4계절, 식생·날씨만 탄다) · 전투는 기존 `duel.js` 재사용 |
| REWORK | 렌더러(Three.js→Godot Node3D/CharacterBody3D) · 카메라(SpringArm3D화) · 지형(손으로 그린 글자 지도 → Godot Terrain/GridMap) |
| MERGE | 없음(GO 고유 시스템은 다른 게임과 안 겹친다) |
| DROP | PLAN1.md의 "슬라임/늑대/고블린/오크/해골" 제네릭 몬스터 목록 — 이 판에 몬스터는 없다, 인물 등용이 그 자리다 |

### SAGA DUNGEON (디아블로 로그라이크)

**핵심 루프**: 내려간다 → 방 치운다 → 은사 고른다 → 장비 챙긴다 → 나온다.
가장 시스템이 복잡한 판 — 디아블로2의 거의 모든 하위 시스템을 한자어로
재해석해 옮겨 놨다.

| 분류 | 내용 |
|---|---|
| KEEP (전부 데이터 기반으로 그대로) | 층/방/은사 로그라이크 루프 · 직업 5종(장착 무기가 직업을 정함, `trait` 아님) · 무예(9모양×5단 스킬트리) · 등급+접사+소켓+부문어(룬워드) · 투장(세트) · 내구/수리 · 행상/투전/연단 · 단약/요대(1234 키) · 감정 · 창고 · 원소 6결+저항(면역 없음, 상한75%) · 인물은 던전에서 등용(출사표3+보스층 합류) · 결사(하드코어) |
| REWORK | 던전 렌더링(2D top-down/isometric → Godot 3D, 이미 `dungeon3d.js`+`field3d.js`로 웹 3D 착수됨 — 그 설계를 Godot 씬 구조로 옮긴다) |
| MERGE | 원소 저항 시스템은 GO의 사건 전투(`duel.js`)와 다르므로 병합 안 함 — DUNGEON 전용으로 남긴다 |
| DROP | PLAN1.md의 "부대/장비/무예/세공/행상/도감/기록" UI 재설계 지시는 이미 실제 메뉴 이름과 거의 일치 — REWORK가 아니라 그대로 UI만 3D 게임 내 Control로 이식 |

### SAGA FOREST (동물의숲)

**핵심 루프**: 걷는다 → 채집한다 → 나눈다(주민과).

| 분류 | 내용 |
|---|---|
| KEEP — 강한 우선순위 | **구면 투영**(루트 CLAUDE.md가 명시적으로 "되돌리지 말라"고 못박은 이 판의 정체성 — 집 안만 평평) · 한 마을 30×20 고정 배치(좌표 해시) · 채집(나무/소나무/바위/꽃 하루1회, 낚시 무제한) · 주민 5명+부탁+선물+편지 · 곤충/화석/조개 채집도감 · 사고(박물관, 도감과 다른 자리) · 순무 장(카부, 유일하게 변동하는 시세) · 벽지/장판 · 꽃 교배(자리 해시) · 계절행사 8일 · 옷(침선방) |
| REWORK | 렌더링만 — 이미 `village-view3d.js`(Three.js)로 PHASE 3까지 진행 중, 그 설계를 Godot으로 이식. **단, "구면 투영"이라는 시각 정체성 자체는 Godot에서도 유지해야 한다**(카메라 왜곡 셰이더나 곡면 지형으로 재현 검토 필요 — 이건 Godot에서 웹의 캔버스 투영 트릭보다 어려울 수 있어 별도 설계 필요) |
| MERGE | 없음 |
| DROP | 없음 — FOREST는 PLAN.md/README와 실제 코드가 가장 일치하는 판이라 버릴 게 적다 |

### SAGA STORY (메이플스토리 사이드스크롤)

**핵심 루프**: 사냥터 진입 → 몬스터 처치 → 성장 → 전직 → 다음 사냥터.
다섯 판 중 유일하게 **2D 사이드스크롤을 3D로 바꾸는 게 렌더링 이상의 문제**다
(플랫포머 물리 자체가 2D 축에 묶여 있다).

| 분류 | 내용 |
|---|---|
| KEEP | 사냥터 4곳(허창들판→오림숲→한중굴혈→호로곡) · 직업 4갈래×3차전직(무명→1차→2차→3차, Lv.10/25/45) · 무예 48(9효과 재사용) · 줄/문 이동 · 급소+경직(0.055초 시간감속) · 사명(퀘스트, 관찰형 카운트) · 물리 상수(중력1900·점프760·달리기270)는 감각의 정체성이라 튜닝값으로 KEEP |
| REWORK | 2D 플랫폼 → 3D. master.md의 saga-story 자체 계획(README)은 이미 "Background/Midground/Foreground + Gameplay Depth"로 **횡스크롤을 유지하되 깊이만 더하는** 절충안을 갖고 있다 — Godot에서도 이 절충(카메라를 한 축에 묶은 3D)을 KEEP하는 게 안전하다. 완전 자유 3D RPG로 바꾸면 플랫포머 정체성 자체가 사라진다 |
| MERGE | 원거리 적(활/조총, 사거리 판정)은 DUNGEON의 몹 AI와 유사 — 공통 Enemy 컴포넌트로 병합 가능 |
| DROP | 없음 |

### SAGA REALM (코에이 삼국지 턴제 전략)

**핵심 루프**: 달마다 명령 → 내정/외교/전쟁 → 승진/등용 → 천하통일.
다섯 판 중 유일하게 **턴제**(rAF 루프 없음) — 3D RPG로 가는 게 아니라 master.md
자체가 "탐험+액션전투를 턴제 경영 위에 얹는" 하이브리드를 이미 README에서
선언했다.

| 분류 | 내용 |
|---|---|
| KEEP — 절대 (다른 판으로 퍼뜨리지 않는다) | 경영·문답(학당)은 REALM 전용 — 루트 CLAUDE.md 금지사항. 시나리오 3개(194/200/208년) · 성 30곳 · 무장 124(공용 70+REALM전용 54) · 내정 9종 · 외교/계략4 · 진영(여러 달 원정, 사기/치중) · 수군(물길·화공·배) · 경험/승진(관직 5단) |
| REWORK | 렌더링 계층만 새로 얹는다(README가 "반드시 재사용: 데이터·무장·성·진영·외교·기록·학당·저장" 목록을 이미 명시) — 판정 코드(`rtk.js`·`war.js`·`officer.js`)는 GDScript로 옮기되 로직은 거의 그대로 이식 가능 |
| MERGE | 없음 — REALM의 경영 시스템은 구조적으로 다른 4판과 안 겹친다 |
| DROP | PLAN1.md/PLAN2.md의 "실시간 액션 전투 중심 RPG" 재정의는 REALM 정체성과 안 맞음 — 실제 README는 "턴제 경영 위에 3D 월드맵과 액션 전투를 붙인다"는 훨씬 절제된 방향이다. **turn-based 경영을 실시간 액션으로 갈아엎지 않는다** |

## 3. 공통 기능 vs 게임별 고유 기능 (master.md 22·23절)

### 정말 공통인 것 (saga_core/ 후보)

- Save/Load 골격(계정·프로필 슬롯 개념 — `account.js` 패턴)
- 진단 하네스 정신(결정적 시드, headless 회귀 테스트)
- 인물 스탯 계산 골격(레벨/경험치/장비보정을 합산하는 함수 형태) — **단, 인물
  데이터 자체(`data.js`)를 공유할지는 사용자 결정 필요(1장 참고)**
- 모바일 세로/가로 대응, 터치 조작 골격

### 게임별로 확실히 분리해야 하는 것

- DUNGEON의 원소/저항/소켓/룬워드 — 로그라이크 파밍 전용
- FOREST의 구면 투영, 채집/주민 시스템 — 생활 시뮬레이션 전용
- STORY의 플랫폼 물리, 전직 트리 — 사이드스크롤 액션 전용
- REALM의 턴제 경영, 외교/전쟁 — 전략 시뮬레이션 전용 (그리고 **문답도 여기만**)
- GO의 소문/사건/발견도감 — 탐험형 전용

이 다섯은 장르가 근본적으로 다르다("Diablo-like" vs "Animal Crossing-like" vs
"turn-based 4X-like"). master.md 6장의 "SAGA Core"가 Combat/Quest/Inventory 같은
**얇은 인터페이스**로 남아야지, 다섯 게임의 실제 규칙을 하나의 시스템으로
합치려 하면 이 감사에서 나온 KEEP 목록 전부가 깨진다.

## 4. 신규 Architecture 반영 (master.md 24절)

`docs/ARCHITECTURE.md`에 아래를 반영해 갱신 필요(다음 세션):

- `saga_core/`는 master.md 6장 목록보다 얇게 — Save·Data(Resource 로더)·Mobile
  Input·Camera 골격 정도만 진짜 공통. Combat/Quest/Inventory는 게임마다 다른
  구현을 갖고 **인터페이스(추상 클래스)만** 공통화
- `games/saga_go/`, `saga_dungeon/` 등 게임별 폴더가 실제 로직 대부분을 갖는다
- `data/`를 다섯 게임이 공유할지 각자 가질지는 미결 — 사용자에게 물을 것

## 6. 인물 데이터 공유 결정 (2026-08-31)

**결정: saga-godot에서는 다섯 게임이 인물 데이터를 공유한다(하나로 통합).**

- `saga_core/data/characters/`에 인물 데이터(원래 다섯 곳에 흩어진 `data.js`의
  인물 70·REALM 전용 무장 54)를 한 벌로 합쳐 둔다
- 인물 **id는 기존 다섯 웹 프로젝트와 동일하게 유지**한다(1장의 "id 불변"
  원칙 — 통합해도 새 id 체계를 만들지 않는다. 다섯 웹판의 id와 saga-godot의
  id가 어긋나면 나중에 데이터를 다시 맞추기 어려워진다)
- **REALM 전용 무장 54(삼국지 군주·부하)는 통합 데이터에도 포함**하되, REALM
  이외의 게임이 그 인물들을 쓸지는 게임별 콘텐츠 설계에서 별도 결정한다
  (통합은 "데이터를 한 곳에 둔다"는 뜻이지 "모든 게임이 모든 인물을 쓴다"는
  뜻이 아니다)
- `sprite.js`(그림 양식)는 공유 대상이 아니다 — 게임마다 다른 렌더 스타일을
  유지한다(1장 반영)
- 기존 다섯 웹 프로젝트(`saga-go` 등)의 `data.js` 다섯 벌 복사 구조는
  이 결정과 무관하게 그대로 둔다 — 이번 통합은 saga-godot 신규 프로젝트에만
  적용된다
