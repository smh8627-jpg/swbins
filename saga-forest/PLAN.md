# saga-forest 3D 오픈 필드 전환 작업

## 0. 최우선 목표

현재 프로젝트를 처음부터 다시 만들지 않는다.

현재 `saga-forest`의 기존 코드, UI, 게임 로직, 데이터 구조를 최대한 보존하면서 **2D/평면형 숲 게임을 3D 오픈 필드 게임으로 점진적으로 전환**한다.

최종적인 게임 방향은 다음과 같다.

> 동물의 숲의 생활형/수집형 게임 + 넓은 3D 자연 필드 + 다양한 바이옴 + 주민 + 탐험 + 채집 + 낚시 + 건축

단, 기존 프로젝트의 코드와 기능을 최대한 재사용하고 필요 없는 부분만 교체한다.

---

# 1. 작업 전 필수 규칙

## 절대 하지 말 것

- 프로젝트 전체를 새로 작성하지 않는다.
- 기존 HTML/CSS/JS를 무조건 삭제하지 않는다.
- 기존 게임 시스템을 새 엔진으로 전부 재작성하지 않는다.
- 기존 UI를 임의로 제거하지 않는다.
- 기존 데이터 구조를 확인하지 않고 새 구조를 강제로 만들지 않는다.
- 동일한 기능을 여러 파일에 중복 구현하지 않는다.
- 사용하지 않는 라이브러리를 대량으로 추가하지 않는다.
- placeholder 코드를 대량 생성하지 않는다.
- 모든 파일을 한 번에 수정하지 않는다.
- 기존 기능이 정상 작동하는데 불필요하게 리팩터링하지 않는다.

# 4. 3D 기술 선택

현재 프로젝트 구조를 먼저 확인한 뒤 가장 적은 변경으로 3D를 구현할 수 있는 방법을 선택한다.

우선순위:

1. 기존 Three.js가 있다면 그대로 사용
2. 없다면 Three.js를 우선 검토
3. 모바일 브라우저에서 안정적인 WebGL 렌더링

5. 필요 이상으로 무거운 엔진 추가 금지

목표는 AAA 게임 엔진을 사용하는 것이 아니라:

> 웹 브라우저에서 실행되는 가벼운 3D 생활형 오픈 필드

이다.

# 5. 3D 월드 구조

현재 좁은 맵을 단순히 확대하지 않는다.

월드를 실제로 넓은 필드처럼 설계한다.

최소 구조:

```text
World
├── Village
├── Forest
├── Meadow
├── River
├── Lake
├── Beach
├── Mountain
├── Cliff
├── Hidden Area
└── Seasonal Area
```

초기 버전에서는 모든 영역을 동시에 고해상도로 생성하지 않는다.

필요한 영역만 생성하는 방식으로 최적화한다.

---

# 6. 맵 크기

현재 맵이 너무 좁기 때문에 월드 크기를 크게 확장한다.

단순히 하나의 거대한 Plane을 만드는 방식은 피한다.

가능하면 다음 구조를 사용한다.

```text
World
 ├── Chunk 0,0
 ├── Chunk 0,1
 ├── Chunk 0,2
 ├── Chunk 1,0
 ├── Chunk 1,1
 ├── Chunk 1,2
 └── ...
```

Chunk 기반 구조를 고려한다.

플레이어 주변 Chunk만 활성화한다.

멀리 있는 Chunk는 비활성화하거나 낮은 품질로 처리한다.

이렇게 해야 모바일에서 성능을 유지하면서 큰 맵을 만들 수 있다.

# 8. 랜덤 월드 생성

월드를 하드코딩하지 않는다.

Seed 기반 랜덤 생성을 사용한다.

예:

```js
worldSeed
```

같은 Seed를 사용하면 동일한 월드를 재생성할 수 있도록 한다.

Seed가 달라지면:

- 나무 위치
- 꽃 위치
- 돌 위치
- 강
- 호수
- 자원
- 주민 위치
- 숨겨진 장소

등이 달라질 수 있도록 구조를 만든다.

단, 초기 구현에서는 지나치게 복잡한 procedural generation을 만들지 않는다.

먼저 안정적인 고정 월드를 만들고 이후 랜덤 요소를 추가한다.

# 9. 바이옴 시스템

다음 구조를 확장 가능한 데이터 기반 시스템으로 만든다.

```js
biomes = {
  forest: {},
  meadow: {},
  beach: {},
  river: {},
  lake: {},
  mountain: {},
  village: {}
}
```

각 바이옴은 다음 정보를 가질 수 있어야 한다.

```text
terrain
trees
plants
rocks
animals
items
music
weather
ambient
```

새로운 바이옴을 추가할 때 기존 코드 수정이 최소화되도록 한다.

# 10. 3D 플레이어

현재 플레이어 시스템을 최대한 유지하면서 3D 이동을 추가한다.

필수 기능:

- WASD
- 모바일 가상 조이스틱
- 이동
- 달리기
- 방향 전환
- 카메라 추적
- 충돌
- 지형 높이에 따른 이동

모바일에서는 화면 전체를 가리는 UI를 만들지 않는다.

---

# 11. 카메라

동물의 숲 스타일의 3D 카메라를 목표로 한다.

기본:

- 3인칭
- 플레이어 추적
- 부드러운 이동
- 줌
- 회전
- 최소/최대 거리 제한
- 지형 내부로 카메라가 들어가지 않도록 처리

모바일 터치:

- 한 손가락: 카메라 회전
- 두 손가락 또는 UI: 줌
- 가상 조이스틱: 이동

초기에는 카메라 기능을 단순하게 구현한다.

---

# 12. GLB / GLTF 모델 시스템

3D 모델을 코드에 직접 하드코딩하지 않는다.

예:

```text
assets/
  models/
    player/
    animals/
    trees/
    buildings/
    items/
    environment/
```

GLB 모델을 로드하는 공통 ModelLoader를 만든다.

예상 구조:

```js
loadModel(path)
```

캐시를 사용한다.

같은 모델을 여러 번 로드하지 않는다.

---

# 13. 모델 다양성

동일한 나무 모델을 수백 개 복제해서 지루한 맵을 만들지 않는다.

예:

```text
tree_01.glb
tree_02.glb
tree_03.glb
tree_04.glb
```

같은 모델이라도:

- scale
- rotation
- position

을 약간씩 변경한다.

가능하면 색상/머티리얼 variation도 사용한다.

# 14. 주민 시스템

3D 모델만 교체 가능한 구조로 만든다.

예:

```js

resident.name
resident.personality
resident.home
resident.schedule
resident.dialogue
```

주민 데이터와 3D 표현을 분리한다.

초기에는 소수의 주민으로 테스트하고 시스템만 확장 가능하게 만든다.

예:

bear

등을 데이터로 관리할 수 있어야 한다.

# 24. 그래픽 스타일

# 25. 성능 최우선

- Object Pool
- Model Cache

# 26. 모바일 최적화

특히 iPhone Safari를 고려한다.

다음 문제가 발생하지 않도록 한다.

- 화면 멈춤
- WebGL context loss
- 메모리 과다 사용
- 과도한 draw call
- 너무 많은 DOM
- 너무 많은 애니메이션
- 너무 큰 텍스처

초기 목표:

> 모바일에서 안정적으로 이동할 수 있는 수준

# 27. 기존 UI 유지

현재 UI의 기능은 최대한 유지한다.

현재 프로젝트에 존재하는:

- 🎒 가방
- 🏡 주민
- 🏠 집
- 📮 편지
- 🪧 공사
- 📖 도감
- 📜 기록

같은 기능을 3D 월드와 연결한다.

UI 디자인 자체를 대규모로 갈아엎지 않는다.

---

# 32. 매우 중요한 개발 방식

각 Phase가 끝날 때 반드시 실행 가능한 상태를 유지한다.

예:

```text
Phase 1
→ 기존 게임 실행 가능

Phase 2
→ 3D 빈 월드 실행 가능

Phase 3
→ 카메라 이동 가능

Phase 4
→ 플레이어 이동 가능

Phase 5
→ 넓은 맵 이동 가능

...
```

한 단계가 깨진 상태에서 다음 단계로 넘어가지 않는다.

# 33. Claude Code 작업 규칙

각 작업 전에 반드시:

```text
1. 관련 파일 검색
2. 최소 범위 분석
3. 변경 파일 목록 결정
4. 수정
5. 실행/검증
6. 오류가 있을 때만 추가 수정
```

순서를 지킨다.

---

# 34. 토큰 절약을 위한 출력 규칙

Claude Code의 설명은 최소화한다.

매 단계마다 긴 설명을 하지 않는다.

다음 형식으로 짧게 보고한다.

```text
[완료]
- 수정 파일:
- 변경 내용:
- 테스트:
- 다음 단계:
```

코드를 설명하기 위해 전체 파일을 출력하지 않는다.

변경된 부분만 설명한다.

---

# 35. 토큰 절약 핵심

다음 행동을 하지 않는다.

```text
❌ 모든 파일 읽기
❌ 모든 파일 요약
❌ 전체 코드 재출력
❌ 이미 알고 있는 코드 다시 설명
❌ 필요 없는 리팩터링
❌ 모든 기능 한 번에 구현
❌ 대량 placeholder 생성
❌ 사용하지 않는 패키지 설치
```

대신:

```text
✅ 검색 → 필요한 부분만 읽기
✅ 최소 수정
✅ 단계별 구현
✅ 기존 코드 재사용
✅ 실제 오류 발생 시만 디버깅
```

# 36. 첫 번째 Claude Code 작업

지금은 전체 게임을 구현하지 않는다.

먼저 아래만 수행한다.

### 작업 1

현재 프로젝트 구조를 분석한다.

### 작업 2

렌더링 방식을 확인한다.

### 작업 3

플레이어/주민/맵/UI/저장 시스템의 위치를 찾는다.

### 작업 4

3D 전환 시 재사용 가능한 파일과 교체해야 할 파일을 구분한다.

### 작업 5

다음 표만 출력한다.

```text
KEEP
- 기존 게임 로직
- 기존 데이터
- 기존 UI
- 기존 저장 시스템

MODIFY
- 맵 렌더링
- 플레이어 렌더링
- 주민 렌더링

NEW
- 3D World
- Camera
- ModelLoader
- Chunk System
- Biome System
```

### 작업 6

아직 코드는 대규모로 수정하지 않는다.

분석 결과를 먼저 보여준다.

# 39. 성공 기준

1. 기존 게임의 핵심 기능이 유지된다.
2. 게임이 3D로 실행된다.
3. 기존보다 월드가 크게 확장된다.
4. 플레이어가 넓은 공간을 자유롭게 이동할 수 있다.
5. 숲/초원/강/호수/해변 등 다양한 공간이 존재한다.
6. 주민과 자연환경을 3D 모델로 확장할 수 있다.
7. GLB 모델을 쉽게 추가할 수 있다.
8. 모바일에서도 실행 가능하다.
9. 기존 저장 데이터가 최대한 유지된다.
10. Claude Code 토큰을 불필요하게 소비하지 않는다.
