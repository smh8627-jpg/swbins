## 0. 최우선 원칙 — 토큰 절약

이번 작업에서 가장 중요한 것은 **불필요한 Claude Code 토큰 사용을 최소화하면서 실제 게임 품질을 크게 향상시키는 것**이다.

반드시 다음 규칙을 지켜라.

- 프로젝트 전체 파일을 무작정 읽지 않는다.
- 작업 시작 전에 디렉터리 구조와 핵심 파일만 먼저 파악한다.
- 필요한 파일만 선택적으로 읽는다.
- 이미 분석한 파일은 같은 세션에서 다시 읽지 않는다.
- 동일한 코드를 여러 번 설명하지 않는다.
- 변경이 필요한 부분만 수정한다.
- 정상적으로 동작하는 기존 시스템을 불필요하게 재작성하지 않는다.
- 기존 코드의 기능을 유지하면서 점진적으로 개선한다.
- 매 단계마다 전체 프로젝트를 다시 분석하지 않는다.
- 작은 수정마다 장황한 설명을 출력하지 않는다.
- 작업 전 반드시 기존 구조를 파악한 후 가장 적은 파일 변경으로 목표를 달성할 방법을 선택한다.
- 새 시스템을 만들기 전에 기존 시스템을 재사용할 수 있는지 먼저 확인한다.
- 에셋 시스템, 렌더링 시스템, UI 시스템, 입력 시스템 등이 이미 존재하면 최대한 재사용한다.
- 같은 기능을 중복 구현하지 않는다.
- 성능에 영향을 주는 무거운 라이브러리를 불필요하게 추가하지 않는다.
- 모바일 성능을 우선한다.

### Claude Code 작업 방식

다음 순서로 진행한다.

1. 프로젝트 구조 확인
2. package.json / 주요 entry point 확인
3. 게임 렌더링 구조 확인
4. 플레이어/맵/카메라/UI 관련 핵심 파일 확인
5. 현재 문제점만 요약
6. 리뉴얼 계획 수립
7. 필요한 파일만 수정
8. 실행/빌드 테스트
9. 오류가 있을 경우 해당 오류와 관련된 파일만 수정
10. 최종적으로 변경사항 요약

**절대로 처음부터 모든 파일을 읽지 마라.**

# 2. 게임 방향

현재 게임의 가장 큰 문제는 다음과 같다.

- 그래픽 품질이 낮다.
- 지형지물이 너무 적다.
- 맵이 비어 있어 플레이 화면이 심심하다.
- 콘텐츠 다양성이 부족하다.
- 모바일 UX가 부족하다.
- 세로/가로 화면 대응이 부족하다.
- 전체적으로 프로토타입 느낌이 강하다.

따라서 목표는 다음과 같다.

## 목표

**“모바일에서 플레이하는 고품질 3D/2.5D 판타지 횡스크롤 액션 RPG”**

분위기는 다음 요소를 참고한다.

- 현대 모바일 RPG
- 고품질 판타지 RPG
- 메이플스토리식 횡스크롤 접근성
- Diablo 계열의 어두운 판타지 분위기
- 캐주얼하지만 풍부한 필드
- 탐험할 이유가 있는 맵
- 다양한 지형지물
- 짧은 시간에도 재미있는 전투
- 모바일에 최적화된 조작

단, 특정 게임을 그대로 복제하지 말고 **독자적인 디자인과 콘텐츠**로 만든다.

# 4. 에셋 사용 원칙

에셋을 무작정 많이 추가해서 로딩이 느려지는 방식은 피한다.

다음 우선순위를 따른다.

1. 기존 프로젝트에 이미 존재하는 에셋
2. 프로젝트 내부 assets 폴더에 추가 가능한 경량 에셋
3. GLB / GLTF 기반 재사용 가능한 3D 에셋
4. 텍스처 아틀라스
5. 반복 사용 가능한 환경 에셋
6. procedural generation을 이용한 보조 요소

가능하면 하나의 환경 에셋을 여러 위치/크기/회전으로 재사용한다.

예:

tree.glb 하나를

- 작은 나무
- 큰 나무
- 죽은 나무
- 희귀 나무

등으로 다양하게 배치한다.

# 6-1. 오버월드 — 마을에서 나가 다른 마을로 + 전체지도 (2026-09-01, 사용자 요청)

사가블로(`../saga-dungeon/PLAN.md` 28-1절)에 적은 것과 같은 방향이다: "던전을
통해 가는 게 아니라 마을 통해서 입구를 나가서 가는 거임, 다른 마을도 가고
다른 지역이라는 개념." 이 판(메이플스토리식)은 원작부터가 **마을↔필드↔마을을
포탈로 잇는 구조**라 이 개념이 가장 자연스럽게 들어맞는 판이다.

- 5절이 이미 "시작 마을 + 초원 + 숲 + 폐허 + 동굴"을 구역으로 나눠 뒀다 — 이걸
  각자 독립된 마을이 아니라 **하나의 사냥터 지역**으로 볼지, 마을을 여럿 두고
  그 사이를 필드로 연결할지는 아직 정하지 않았다.
- 디아블로 M키처럼 **미니맵을 펼쳐 보는 전체 지도**도 같이 필요하다 — 지금까지
  밟은 사냥터/마을이 오버월드의 어디에 있는지 한눈에 보여주는 것.

**착수함(2026-09-02).** 사용자가 "마을을 여러 개로 늘려 각 구역 초입에 배치"를
골랐다. 삼국지 실제 지명으로 마을 다섯을 새로 넣고 기존 사냥터 넷 사이에
끼워 넣었다(`js/data-side.js` STAGES) —

```
신야성(시작) → 허도 → 허창 들판 → 강릉진 → 오림 숲
             → 남정성 → 한중 굴혈 → 기산채 → 호로곡
```

- 마을은 `town:true` 만 붙은 사냥터 항목이다 — 옆으로 걷기·문(포탈)·발판 엔진은
  그대로 쓰고 `spawn:0`·보스 없음으로 전투만 뺐다(따로 엔진을 새로 만들지 않았다).
  각 마을의 `need` 는 그 마을이 지키는 사냥터와 같아 레벨 문턱이 그대로 이어진다.
- 새 세이브 기본 위치를 `field` 에서 `sinya`(신야성)로 바꿨다(`js/side.js`).
  기존 세이브는 이미 있던 스테이지 키(field/forest/cave/gorge)를 그대로 쓰므로
  깨지지 않는다.
- `js/ui.js`에 **M키(데스크톱) + 상단 도구줄 🗺️ 버튼(모바일) + 사냥터 시트 안
  "🗺️ 전체 지도" 단추**로 여는 오버월드 전체 지도(`#owmap`, `openOverworldMap`)를
  새로 넣었다. 9칸(마을 5 + 사냥터 4)을 사슬로 그리고 지금 있는 곳을 금빛으로,
  잠긴 곳은 흐리게 보여 준다 — 읽기 전용(이동 버튼 없음).
  `viewField()`의 던전-게임 `viewWorldMap()`류와 겹치는 이름은 없다(이 판엔
  애초에 그 개념이 없었다).
- 자가진단(`_test.html`)도 새 구조에 맞춰 고쳤다: 문 하나짜리 이동 검증은
  '들판→강릉진'으로, 넷째 계단 검사는 `town:true` 를 뺀 사냥터 넷만 보게,
  기존 '굴혈→호로곡' 단발 사슬 검사는 '신야성→…→호로곡' 전체 9칸 사슬을
  한 칸씩 걸어보는 항목으로 넓혔다. 헤드리스 3회 106/106 동일.

# 7. 지형지물 다양성

맵을 볼 때 매번 똑같은 나무만 반복되는 느낌을 없앤다.

환경 오브젝트를 category별로 관리한다.

```text
Environment
├── Nature
│   ├── Trees
│   ├── Grass
│   ├── Flowers
│   ├── Bushes
│   ├── Mushrooms
│   └── Rocks
│
├── Structures
│   ├── Houses
│   ├── Fences
│   ├── Bridges
│   ├── Ruins
│   └── Signs
│
├── Props
│   ├── Barrels
│   ├── Crates
│   ├── Lanterns
│   ├── Torches
│   └── Wells
│
└── Landmarks
    ├── Waterfall
    ├── AncientTree
    ├── Ruins
    └── CaveEntrance
```

가능하면 데이터 기반으로 배치한다.

- 마법형
- 희귀형
- 보스형

초기 구현에서는 3~4종만 만들어도 된다.

중요한 것은 **몬스터 타입을 쉽게 추가할 수 있는 구조**다.

---

# 14. 보스 콘텐츠

필드의 특정 지역에 보스가 등장할 수 있도록 만든다.

보스는 일반 몬스터와 확실하게 구분된다.

예:

- 대형 모델
- 별도 HP bar
- 보스 이름
- 공격 패턴
- 바닥 범위 표시
- 강한 이펙트
- 사망 연출
- 보상

---

# 15. 퀘스트 시스템

스토리 게임이라는 이름에 맞게 콘텐츠를 강화한다.

퀘스트 종류:

- NPC 대화
- 이동
- 몬스터 처치
- 아이템 수집
- 특정 장소 방문
- 보스 처치
- 탐험

퀘스트 UI에는

- 현재 목표
- 진행도
- 보상
- 완료 상태

를 표시한다.

---

# 16. 스토리 연출

단순한 텍스트 창만 띄우지 않는다.

가능하다면

- 캐릭터 portrait
- 대화창
- 이름
- 감정 표현
- 카메라 이동
- 간단한 연출
- 화면 전환

등을 사용한다.

다만 대화 연출 때문에 성능이 떨어지지 않도록 한다.

---

# 17. 모바일 세로/가로 모드

**반드시 세로와 가로를 모두 지원한다.**

## 세로 모드

- 한 손 플레이
- 플레이어 중심
- 큰 조작 버튼
- 최소한의 UI
- 세로 화면에 맞는 HUD

## 가로 모드

- 더 넓은 시야
- 좌측 이동 컨트롤
- 우측 공격/스킬
- 더 넓은 HUD
- 더 많은 게임 화면

orientation 변경 시 게임이 깨지지 않아야 한다.

CSS media query 및 JavaScript resize/orientation 이벤트를 적절히 사용한다.

---

# 18. 모바일 컨트롤

모바일 터치 조작을 우선한다.

### 왼쪽

가상 조이스틱

### 오른쪽

- 기본 공격
- 스킬 1
- 스킬 2
- 회피

필요하면 버튼 크기를 화면 크기에 따라 자동 조절한다.

터치 영역은 충분히 크게 한다.

---

# 19. 데스크톱도 유지

PC에서도 플레이 가능해야 한다.

지원:

- WASD
- 방향키
- 마우스
- 키보드 스킬

모바일과 PC 입력 시스템을 하나의 abstraction으로 관리한다.

---

# 20. 카메라

횡스크롤 게임의 장점을 유지하되 3D 공간감을 강화한다.

카메라는 다음을 지원하도록 한다.

- 플레이어 추적
- 부드러운 이동
- 제한 영역
- 지역별 카메라 범위
- 보스전 확대/연출
- 화면 흔들림
- 스킬 사용 시 약간의 카메라 연출

카메라가 지나치게 흔들려 모바일에서 불편하지 않도록 한다.

---

# 21. 3D/2.5D 방향

완전한 자유 시점 3D가 아니라도 된다.

오히려 모바일에서는 **2.5D + 3D 에셋**을 적극적으로 활용한다.

목표:

- 3D 캐릭터
- 3D 환경
- 깊이감 있는 배경
- 횡스크롤 중심 플레이
- 약간의 카메라 각도
- 자연스러운 그림자

이 방식으로 그래픽 품질과 모바일 성능을 동시에 확보한다.

---

# 22. 조명

기본 조명 하나만 사용하는 느낌을 없앤다.

가능하면 다음을 사용한다.

- Directional Light
- Ambient Light
- 지역별 조명
- 횃불 Point Light
- 동굴의 어두운 조명
- 마을의 따뜻한 조명

단, 모바일에서 실시간 광원을 과도하게 사용하지 않는다.

---

# 23. 그림자

그림자는 중요한 오브젝트 중심으로 적용한다.

모든 오브젝트가 고해상도 그림자를 사용하는 방식은 금지한다.

성능 우선:

- 플레이어
- 주요 몬스터
- 주요 환경물

위주로 그림자를 적용한다.

---

# 24. 그래픽 후처리

가능하다면 최소한의 후처리를 사용한다.

- Ambient Occlusion 느낌
- Bloom
- 색감 보정
- 안개
- 거리감

단, 모바일 저사양에서 자동으로 효과를 줄일 수 있도록 한다.

---

# 25. 성능 최적화

모바일 게임이므로 매우 중요하다.

반드시 고려한다.

- object pooling
- frustum culling
- LOD
- texture compression
- asset lazy loading
- 필요할 때만 애니메이션 업데이트
- 보이지 않는 NPC/몬스터 업데이트 최소화
- 파티클 수 제한
- draw call 감소
- 동일 모델 instancing/reuse
- 큰 텍스처 남발 금지

---

# 26. 반응형 그래픽 품질

기기 성능에 따라 자동으로 그래픽 품질을 조절할 수 있도록 만든다.

### Low

- 그림자 최소
- 파티클 감소
- 효과 감소
- 낮은 해상도

### Medium

- 기본 그림자
- 기본 파티클
- 일반 효과

### High

- 그림자 강화
- 파티클 증가
- 후처리
- 고품질 효과

초기에는 자동 감지 또는 기본 Medium을 사용한다.

---

# 27. 로딩 최적화

처음 접속했을 때 모든 에셋을 한꺼번에 로드하지 않는다.

# 41. 최종 지시

이 프로젝트는 단순한 웹 프로토타입을 만드는 것이 목적이 아니다.

**“모바일에서 실제로 플레이하고 싶어지는 게임”처럼 보이게 만드는 것​**이 최종 목표다.

특히 현재 가장 부족한 것은:

1. 그래픽
2. 지형지물
3. 맵의 풍부함
4. 콘텐츠 다양성
5. 모바일 UX
6. 세로/가로 대응
7. 전반적인 완성도

이다.

따라서 기능 숫자만 늘리지 말고 **첫 화면을 보는 순간 품질 차이가 느껴지도록 시각적 완성도를 먼저 끌어올려라.**

단,

**토큰 절약 > 기존 코드 재사용 > 성능 > 기능 추가 > 세부적인 polish**

순서로 판단한다.

한 번에 모든 기능을 완성하려 하지 말고, 현재 프로젝트에서 가장 적은 코드 변경으로 가장 큰 품질 향상을 만드는 방향으로 작업한다.

작업 중 기존 구조가 예상과 다르면 억지로 계획을 적용하지 말고 실제 코드 구조에 맞춰 수정한다.

최종적으로 반드시 실제 실행 및 모바일 반응형을 확인하고, 문제가 있는 부분만 추가 수정한다.

# 부록 · 코드로 그리지 말고 에셋으로 (다섯 판 공통 방침)

**사용자 지시 (2026-08-28). 다섯 판에 다 같이 적용한다.**

> "스크립트로 쓰고 있는 것들은 다 에셋으로 변경 했으면 해."
> "스크립트는 오직 이벤트나 기능들."
> "도감 일러스트나 캐릭터들도 에셋이 없는지 확인해주고 추가해줘. UI 도."

즉 **코드가 도형·그림을 조립해 만들던 것은 전부 실제 에셋으로 갈아 끼운다.**
3D 모델만이 아니다 — **도감 일러스트 · 인물 초상 · UI 그림**까지 포함한다.
남는 스크립트는 **이벤트와 기능(판정 · 규칙 · 상태)** 뿐이다.

## 왜

사용자가 먼저 고른 것이 **품질**이다. "스크립트로 그려서 퀄리티가 떨어진다 —
에셋을 써라" 가 이 축의 시작이었고, 받을 수 있는 CC0 에셋이 이 판의 결
(한옥 · 갓 · 도포)과 다르다는 것을 알고도 **"둘 다 얹는다(품질 우선)"** 를 골랐다.
그러니 **"결이 안 맞아서" 는 안 하는 이유가 되지 못한다.**

## 어떻게

- 새 작업을 잡을 때 **그 판에서 아직 코드가 그리는 것부터 센다.**
  3D 소품 · 건물 · 인물뿐 아니라 **캔버스로 그리는 초상 · 카드 · 아이콘**까지
- **되돌림 길은 지우지 말고 손잡이로 남긴다.** 에셋을 못 받는 자리가 실제로 있다 —
  `file://` 단독판 · 낮은 품질 등급 · 오프라인. 그때는 조용히 옛 그림으로 돌아간다
- **에셋을 못 구하면 그 사실을 알린다.** 이 망은 GitHub(`raw.githubusercontent.com` ·
  `api.github.com`)만 열려서 미러에 없는 것은 못 받는다. CC0 로 존재하지 않는 것
  (예: 특정 인물 일흔의 초상)은 **"안 한다" 가 아니라 "이래서 막혔고 대신 이것을
  할 수 있다"** 로 보고한다 — 사용자가 직접 받아다 줄 수도 있다
- 출처와 라이선스는 판마다 `assets/ASSET_LICENSES.md` 에 적는다.
  **공개 저장소라 재배포가 안 되는 것은 애초에 받지 않는다.**
  저작자 표시가 필수인 것(CC-BY)은 표시 문구를 같이 옮긴다
- **원작사의 실제 에셋은 넣지 않는다.** 이 규칙은 그대로다
