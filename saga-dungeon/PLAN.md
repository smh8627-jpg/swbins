# SAGA-DUNGEON 대규모 3D 리뉴얼 작업 지시서

대상 프로젝트:

https://smh8627-jpg.github.io/swbins/saga-dungeon/

## 최우선 원칙

현재 프로젝트를 처음부터 새로 만들지 않는다.

기존 코드와 시스템을 최대한 분석하고 재사용하면서,
현재 `saga-dungeon`을 현대적인 **3D 모바일 액션 RPG**로 단계적으로 업그레이드한다.

목표는 단순한 3D 적용이 아니다.

현재 게임의 가장 큰 문제인:

- 그래픽 퀄리티 부족
- 지형지물 부족
- 맵이 비어 보임
- 전투 외 콘텐츠 부족
- 반복 플레이 재미 부족
- 모바일 UI 부족
- 세로/가로 화면 대응 부족
- 전체적인 게임 완성도 부족

을 동시에 해결한다.

# 1. 절대적인 토큰 절약 규칙

Claude Code 작업에서 가장 중요한 우선순위다.

## 반드시 지킬 것

1. 기존 파일을 먼저 분석한다.
2. 이미 존재하는 기능을 다시 만들지 않는다.
3. 기존 시스템을 삭제하고 처음부터 작성하지 않는다.
4. 필요한 파일만 수정한다.
5. 대규모 파일 전체 재작성 금지.
6. 작은 단위의 패치 방식으로 작업한다.
7. 같은 코드를 여러 파일에 복사하지 않는다.
8. 공통 기능은 기존 utility/module을 재사용한다.
9. 새로운 라이브러리는 반드시 필요한 경우에만 추가한다.
10. 이미 설치된 라이브러리가 있다면 그것을 우선 사용한다.
11. 기존 데이터 구조를 최대한 유지한다.
12. 기존 UI/게임 로직 중 정상 작동하는 부분은 건드리지 않는다.
13. 작업 전 전체 프로젝트를 무작정 읽지 않는다.
14. 먼저 파일 구조와 entry point를 확인한다.
15. 그 다음 실제 수정에 필요한 파일만 읽는다.
16. 각 단계마다 변경 파일을 최소화한다.
17. 동일한 파일을 여러 번 전체 출력하지 않는다.
18. 코드 설명보다 실제 수정 작업을 우선한다.
19. 긴 주석을 남발하지 않는다.
20. 사용하지 않는 코드와 asset을 추가하지 않는다.

## Claude Code 작업 방식

매 단계마다 다음 순서로 진행한다.

1. 현재 구조 확인
2. 관련 파일만 읽기
3. 기존 기능 재사용 여부 판단
4. 최소 수정
5. 실행/빌드 확인
6. 오류 수정
7. 다음 단계 진행

절대로 한 번에 전체 프로젝트를 갈아엎지 않는다.

# 5. Asset Loader 구축

3D asset을 각 시스템에서 개별적으로 로드하지 않는다.

공통 AssetManager를 만든다.

예:

AssetManager
- preload()
- loadGLB()
- get()
- has()
- dispose()
- clearUnused()

동일한 모델은 반드시 캐싱한다.

같은 나무 50개를 만들더라도 GLB를 50번 로드하지 않는다.

가능하면:

- InstancedMesh
- Object3D clone
- shared geometry
- shared material

을 사용한다.

# 22. 세로 / 가로 모두 지원

반드시 지원한다.

CSS:

```css
@media (orientation: portrait) {
  /* portrait layout */
}

@media (orientation: landscape) {
  /* landscape layout */
}
```

JavaScript에서는 현재 orientation을 감지해서 UI 레이아웃을 전환한다.

가능한 환경에서는 Screen Orientation API를 사용하되 특정 방향을 강제로 고정하지 않는다.

세로와 가로 모두 플레이 가능해야 한다.

브라우저가 orientation lock을 지원하지 않는 경우에도 게임은 정상적으로 작동해야 한다.

Screen Orientation API의 지원 여부가 브라우저마다 다르므로 fallback을 반드시 구현한다.

### 28-1. 오버월드 — 마을에서 나가 다른 마을로 (2026-09-01, 사용자 요청)

**지금 있는 것과 헷갈리지 말 것.** `js/ui.js` `viewWorldMap()`(🗺️ 월드맵 시트)은
이미 있지만, 이건 **던전 층 테마 진행표**다(고분→폐성→산채→수궁→지옥문→천계,
몇 층까지 밟았는지 잠금/답파만 보여 준다). 아래는 그것과 다른, 아직 없는 개념이다.

**요지 — 사용자 말 그대로:** "던전을 통해 가는 게 아니라 마을 통해서 입구를
나가서 가는 거임, 다른 마을도 가고 다른 지역이라는 개념." 즉:

- 마을(본영)에는 **던전 굴혈 입구 말고 또 다른 출구(들판 입구)**가 있고,
  그리로 나가면 필드를 거쳐 **다른 마을**에 닿는다.
- "지역"은 던전 층 테마가 아니라 **마을 하나하나가 곧 지역**이다 — 여러 마을을
  오갈 수 있는 오버월드.
- 참고 삼아: 디아블로도 이 구조다 — 마을(캠프/성역)에서 필드로 나가 액트별
  구역·웨이포인트로 이어진다. 던전은 마을에 딸린 곁가지고, 마을↔마을(지역) 이동이
  본체다.

### 28-2. 전체 오픈월드 — 설계안 (아직 미구현, 2026-09-05 작성, 사용자 검토 대기)

README가 명시하는 장기 목표("마을↔마을이 끊기지 않고 전부 걸어서 이어지는 전체
오픈월드")를 향한 **설계 문서다. 이 절만으로는 아무것도 안 바뀐다** — 코드는
한 줄도 안 건드렸다. 다음에 착수할 세션이 여기서 바로 Phase 1을 시작할 수
있게 적는다.

**지금 마을 간 이동은 순간이동이다 — 코드로 확인했다.** `js/town.js`의
`travel(markKey)`는 `CURRENT_TOWN`을 바꾸고 `build()`를 다시 불러 **완전히
새 방을 처음부터 재구성**한다 — 좌표는 마을마다 매번 `BASE_W×BASE_H` 기준
같은 상대 좌표계로 리셋되고(`scalePt()`), 페이드나 로딩 화면 없이
`ui.js`의 `town:mark` 리스너가 그 프레임 안에서 즉시 `travel()`을 부른다.
즉 **네 마을은 각자 독립된 좌표 공간**이고, 지금 있는 "오버월드"(28-1절)는
그 사이를 순간이동으로 잇는 상위 배치도일 뿐 진짜 이어진 하나의 공간이
아니다. 들판 생성(`field3d.js`의 `chunkAt(cx,cz,seed,ring,dens,theme)`)도
마을마다 독립된 씨앗 공간이라 마을 A의 (500,500)과 마을 B의 (500,500)은
아무 관계가 없다.

**두 갈래 접근을 검토했다.**

**A안 — 단일 연속 좌표계.** 마을 넷을 하나의 거대한 좌표 공간에 실제
거리를 두고 배치하고, 그 사이를 `chunkAt()`으로 채운 필드로 실제로
걸어서 지나간다. 정말로 "이어진" 세상이 되지만:
- 좌표계·POI 배치(`dungeon.js`의 필드 POI, 마을 exit 좌표)·세이브
  스키마(`core.save.town`은 지금 "마을 id 하나"만 담는다, 연속 좌표계면
  플레이어의 절대 좌표를 저장해야 한다)·충돌판정(`fieldBlockedAt`)을
  전부 다시 설계해야 한다.
- 마을 넷 각각을 독립 좌표계로 두는 지금 구조는 **이미 검증된 자산**이다
  (오버월드 235/235 자가진단, 실기기 확인 이력). 이걸 버리는 건 PLAN
  §1·§44·§49가 반복해서 금지하는 "전체 재작성"에 정확히 해당한다.
- **결론 — 최소 패치로 불가능하다.** 이 프로젝트의 반복된 원칙과 정면
  충돌하므로 권장하지 않는다.

**B안 — 위장된 전환(권장).** 마을마다 독립 좌표계는 그대로 두되, 들길
표식을 순간이동 트리거가 아니라 **"전환 통로"** 진입점으로 바꾼다:
- 들길을 밟으면 그 방향의 테마 있는 좁은 필드 조각(숲길·고갯길·나루터
  등, `field3d.js`의 `chunkAt()`이 이미 그리는 결 그대로, 폭만 좁게)을
  걷게 하고, 이 구간의 반대쪽 끝에 닿으면 그제서야 `travel()`(지금 있는
  순간이동 로직 그대로)을 부른다.
- 이미 있는 인프라를 거의 그대로 재사용한다 — 씨앗 기반 청크 생성
  (`chunkAt`), 마을 로딩 우선순위(`prefetchTownDest`, 이번 세션에서
  이미 만듦, 통로 진입 시점에 미리 부르면 된다), 세이브 스키마(여전히
  "마을 id 하나"로 충분 — 통로 자체는 저장할 상태가 없다, 통로 중간에
  나가면 다시 시작 지점에서 출발해도 무방하다).
- 화면 전환(로딩 화면 없음, 순간이동 없음)이라는 체감만 얻고, 좌표계·
  POI·충돌판정·세이브 구조는 **단 하나도 안 바꾼다** — PLAN §49의
  "기존 기능 재사용 > 최소 수정" 순서를 그대로 지킨다.
- **주의** — 사용자가 말한 "오픈월드"가 반드시 A안(하나의 좌표계)을
  뜻하는 게 아닐 수 있다. "걸어서 이어진다"는 체감이 핵심이라면 B안이
  그 체감을 훨씬 적은 리스크로 준다. A안이 정말 필요하다면(예: 미니맵에
  네 마을을 한 화면의 실제 거리로 보여줘야 하는 등) 그건 이 설계안과
  별도로 사용자에게 다시 확인받을 것.

**위험 요소 — 반드시 확인할 것:**
- **RNG 순번 함정** (이번 세션 내내 여러 번 겪었다) — `chunkAt()`은
  순수 함수지만 통로 생성이 새 좌표 구간에서 `core.hash2`/`Math.random`을
  추가로 소비하면 자가진단 시드(mulberry32, 20260824) 수열이 밀려
  무관한 항목이 깨질 수 있다. 새 판정에 RNG가 필요하면 반드시
  `core.hash2(고정입력...)` 순수 해시로, 자가진단 항목은 **파일 맨
  끝에 추가**하고 앞선 테스트가 남긴 상태(부대 비움 등)에 의존하지
  않게 짤 것 — 지역 도감 사이클(커밋 `1e40dbf`)이 겪은 함정 그대로다.
- **세이브 스키마** — `core.save.town.current`는 "지금 있는 마을 id"만
  담는다. 통로 중간에 게임을 끄면 어디서 이어야 하는지 정책을 정할
  것(가장 단순한 답: 통로엔 세이브 지점이 없다, 다음 로드 때 출발
  마을로 되돌린다 — Phase 1에서 미리 정해 둘 것).
- **오버월드 지도(M키)와의 정합성** — `overworld.list()`가 보여주는
  고정 3×3 배치가 "통로로 이어진 인접 마을"이라는 인상과 안 어긋나는지
  (지금은 별형 연결이라 위성 셋끼리는 안 잇는다 — 통로도 위성↔모루골
  방향에만 생긴다, 위성↔위성 통로는 이 설계안 범위 밖).

**검증 계획(공통)** — 매 Phase마다 `_test.html` RESULT n/n 세 번 동일,
`_admin.html?selftest` ADMIN n/n, 필요하면 CDP로 통로 진입~반대쪽 끝
도달까지 걸어보는 시나리오, 3D는 헤드리스 스크린샷(무거운 실제 장면이
죽으면 고립 렌더 페이지로 대체). 한 Phase가 끝나기 전엔 다음 Phase로
안 넘어간다(PLAN §46).

# Claude Code 실행 지침

지금 바로 코드를 수정하기 전에 먼저 프로젝트 구조를 분석한다.

전체 프로젝트를 한꺼번에 읽지 말고 entry point와 핵심 파일부터 찾는다.

그 다음 현재 기능 중 재사용 가능한 부분을 판단한다.

그리고 Phase 1부터 순서대로 진행한다.

각 Phase마다 실제 코드를 수정하고 검증한다.

**가장 중요한 것은 토큰 절약이다.**

불필요한 파일을 읽거나 전체 코드를 반복 출력하지 않는다.

작업 중 이미 확인한 파일은 다시 전체를 읽지 않는다.

변경이 필요한 부분만 읽고 수정한다.

작업 결과를 장황하게 설명하지 말고 실제 구현에 집중한다.

단, 중요한 구조 변경이나 에셋 추가가 필요한 경우에는 짧게 이유만 기록한다.

최종 목표는 기존 `saga-dungeon`의 게임 시스템을 버리는 것이 아니라,

**기존 시스템 + 실제 3D 에셋 + 넓은 필드 + 다양한 환경 + 랜덤 콘텐츠 + 모바일 세로/가로 지원 + 고품질 액션 전투**

를 결합하여 완전히 새로운 수준의 SAGA-DUNGEON으로 만드는 것이다.

# 부록 · 코드로 그리지 말고 에셋으로 (다섯 판 공통 방침)

**사용자 지시 (2026-08-28). 다섯 판에 다 같이 적용한다.**

> "스크립트로 쓰고 있는 것들은 다 에셋으로 변경 했으면 해."
> "스크립트는 오직 이벤트나 기능들."
> "도감 일러스트나 캐릭터들도 에셋이 없는지 확인해주고 추가해줘. UI 도."

즉 **코드가 도형·그림을 조립해 만들던 것은 전부 실제 에셋으로 갈아 끼운다.**
3D 모델만이 아니다 — **도감 일러스트 · 인물 초상 · UI 그림**까지 포함한다.
남는 스크립트는 **이벤트와 기능(판정 · 규칙 · 상태)** 뿐이다.

## 왜

사용자가 먼저 고른 것이 **품질**이다. "스크립트로 그려서 퀄리티가 떨어진다 —
에셋을 써라" 가 이 축의 시작이었고, 받을 수 있는 CC0 에셋이 이 판의 결
(한옥 · 갓 · 도포)과 다르다는 것을 알고도 **"둘 다 얹는다(품질 우선)"** 를 골랐다.
그러니 **"결이 안 맞아서" 는 안 하는 이유가 되지 못한다.**

## 어떻게

- 새 작업을 잡을 때 **그 판에서 아직 코드가 그리는 것부터 센다.**
  3D 소품 · 건물 · 인물뿐 아니라 **캔버스로 그리는 초상 · 카드 · 아이콘**까지
- **되돌림 길은 지우지 말고 손잡이로 남긴다.** 에셋을 못 받는 자리가 실제로 있다 —
  `file://` 단독판 · 낮은 품질 등급 · 오프라인. 그때는 조용히 옛 그림으로 돌아간다
- **에셋을 못 구하면 그 사실을 알린다.** 이 망은 GitHub(`raw.githubusercontent.com` ·
  `api.github.com`)만 열려서 미러에 없는 것은 못 받는다. CC0 로 존재하지 않는 것
  (예: 특정 인물 일흔의 초상)은 **"안 한다" 가 아니라 "이래서 막혔고 대신 이것을
  할 수 있다"** 로 보고한다 — 사용자가 직접 받아다 줄 수도 있다
- 출처와 라이선스는 판마다 `assets/ASSET_LICENSES.md` 에 적는다.
  **공개 저장소라 재배포가 안 되는 것은 애초에 받지 않는다.**
  저작자 표시가 필수인 것(CC-BY)은 표시 문구를 같이 옮긴다
- **원작사의 실제 에셋은 넣지 않는다.** 이 규칙은 그대로다
