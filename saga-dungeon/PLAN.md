# SAGA-DUNGEON 대규모 3D 리뉴얼 작업 지시서

대상 프로젝트:

https://smh8627-jpg.github.io/swbins/saga-dungeon/

## 최우선 원칙

현재 프로젝트를 처음부터 새로 만들지 않는다.

기존 코드와 시스템을 최대한 분석하고 재사용하면서,
현재 `saga-dungeon`을 현대적인 **3D 모바일 액션 RPG**로 단계적으로 업그레이드한다.

목표는 단순한 3D 적용이 아니다.

현재 게임의 가장 큰 문제인:

- 그래픽 퀄리티 부족
- 지형지물 부족
- 맵이 비어 보임
- 전투 외 콘텐츠 부족
- 반복 플레이 재미 부족
- 모바일 UI 부족
- 세로/가로 화면 대응 부족
- 전체적인 게임 완성도 부족

을 동시에 해결한다.

# 1. 절대적인 토큰 절약 규칙

Claude Code 작업에서 가장 중요한 우선순위다.

## 반드시 지킬 것

1. 기존 파일을 먼저 분석한다.
2. 이미 존재하는 기능을 다시 만들지 않는다.
3. 기존 시스템을 삭제하고 처음부터 작성하지 않는다.
4. 필요한 파일만 수정한다.
5. 대규모 파일 전체 재작성 금지.
6. 작은 단위의 패치 방식으로 작업한다.
7. 같은 코드를 여러 파일에 복사하지 않는다.
8. 공통 기능은 기존 utility/module을 재사용한다.
9. 새로운 라이브러리는 반드시 필요한 경우에만 추가한다.
10. 이미 설치된 라이브러리가 있다면 그것을 우선 사용한다.
11. 기존 데이터 구조를 최대한 유지한다.
12. 기존 UI/게임 로직 중 정상 작동하는 부분은 건드리지 않는다.
13. 작업 전 전체 프로젝트를 무작정 읽지 않는다.
14. 먼저 파일 구조와 entry point를 확인한다.
15. 그 다음 실제 수정에 필요한 파일만 읽는다.
16. 각 단계마다 변경 파일을 최소화한다.
17. 동일한 파일을 여러 번 전체 출력하지 않는다.
18. 코드 설명보다 실제 수정 작업을 우선한다.
19. 긴 주석을 남발하지 않는다.
20. 사용하지 않는 코드와 asset을 추가하지 않는다.

## Claude Code 작업 방식

매 단계마다 다음 순서로 진행한다.

1. 현재 구조 확인
2. 관련 파일만 읽기
3. 기존 기능 재사용 여부 판단
4. 최소 수정
5. 실행/빌드 확인
6. 오류 수정
7. 다음 단계 진행

절대로 한 번에 전체 프로젝트를 갈아엎지 않는다.

# 5. Asset Loader 구축

3D asset을 각 시스템에서 개별적으로 로드하지 않는다.

공통 AssetManager를 만든다.

예:

AssetManager
- preload()
- loadGLB()
- get()
- has()
- dispose()
- clearUnused()

동일한 모델은 반드시 캐싱한다.

같은 나무 50개를 만들더라도 GLB를 50번 로드하지 않는다.

가능하면:

- InstancedMesh
- Object3D clone
- shared geometry
- shared material

을 사용한다.

# 22. 세로 / 가로 모두 지원

반드시 지원한다.

CSS:

```css
@media (orientation: portrait) {
  /* portrait layout */
}

@media (orientation: landscape) {
  /* landscape layout */
}
```

JavaScript에서는 현재 orientation을 감지해서 UI 레이아웃을 전환한다.

가능한 환경에서는 Screen Orientation API를 사용하되 특정 방향을 강제로 고정하지 않는다.

세로와 가로 모두 플레이 가능해야 한다.

브라우저가 orientation lock을 지원하지 않는 경우에도 게임은 정상적으로 작동해야 한다.

Screen Orientation API의 지원 여부가 브라우저마다 다르므로 fallback을 반드시 구현한다.

### 28-1. 오버월드 — 마을에서 나가 다른 마을로 (2026-09-01, 사용자 요청)

**지금 있는 것과 헷갈리지 말 것.** `js/ui.js` `viewWorldMap()`(🗺️ 월드맵 시트)은
이미 있지만, 이건 **던전 층 테마 진행표**다(고분→폐성→산채→수궁→지옥문→천계,
몇 층까지 밟았는지 잠금/답파만 보여 준다). 아래는 그것과 다른, 아직 없는 개념이다.

**요지 — 사용자 말 그대로:** "던전을 통해 가는 게 아니라 마을 통해서 입구를
나가서 가는 거임, 다른 마을도 가고 다른 지역이라는 개념." 즉:

- 마을(본영)에는 **던전 굴혈 입구 말고 또 다른 출구(들판 입구)**가 있고,
  그리로 나가면 필드를 거쳐 **다른 마을**에 닿는다.
- "지역"은 던전 층 테마가 아니라 **마을 하나하나가 곧 지역**이다 — 여러 마을을
  오갈 수 있는 오버월드.
- 참고 삼아: 디아블로도 이 구조다 — 마을(캠프/성역)에서 필드로 나가 액트별
  구역·웨이포인트로 이어진다. 던전은 마을에 딸린 곁가지고, 마을↔마을(지역) 이동이
  본체다.

### 28-2. 전체 오픈월드 — 통로형 전환 (2026-09-05, 설계 후 Phase 1~4 전부 구현 완료)

README가 명시하는 장기 목표("마을↔마을이 끊기지 않고 전부 걸어서 이어지는 전체
오픈월드")를 향한 절이다. **처음엔 설계 문서로만 적어 뒀지만(2026-09-05 최초
작성), 사용자가 그 자리에서 바로 Phase 1~4를 순서대로 승인해 전부 구현까지
끝냈다** — 아래는 그 설계 근거와 실제로 구현한 내용을 함께 담는다.

**지금 마을 간 이동은 순간이동이다 — 코드로 확인했다.** `js/town.js`의
`travel(markKey)`는 `CURRENT_TOWN`을 바꾸고 `build()`를 다시 불러 **완전히
새 방을 처음부터 재구성**한다 — 좌표는 마을마다 매번 `BASE_W×BASE_H` 기준
같은 상대 좌표계로 리셋되고(`scalePt()`), 페이드나 로딩 화면 없이
`ui.js`의 `town:mark` 리스너가 그 프레임 안에서 즉시 `travel()`을 부른다.
즉 **네 마을은 각자 독립된 좌표 공간**이고, 지금 있는 "오버월드"(28-1절)는
그 사이를 순간이동으로 잇는 상위 배치도일 뿐 진짜 이어진 하나의 공간이
아니다. 들판 생성(`field3d.js`의 `chunkAt(cx,cz,seed,ring,dens,theme)`)도
마을마다 독립된 씨앗 공간이라 마을 A의 (500,500)과 마을 B의 (500,500)은
아무 관계가 없다.

**두 갈래 접근을 검토했다.**

**A안 — 단일 연속 좌표계.** 마을 넷을 하나의 거대한 좌표 공간에 실제
거리를 두고 배치하고, 그 사이를 `chunkAt()`으로 채운 필드로 실제로
걸어서 지나간다. 정말로 "이어진" 세상이 되지만:
- 좌표계·POI 배치(`dungeon.js`의 필드 POI, 마을 exit 좌표)·세이브
  스키마(`core.save.town`은 지금 "마을 id 하나"만 담는다, 연속 좌표계면
  플레이어의 절대 좌표를 저장해야 한다)·충돌판정(`fieldBlockedAt`)을
  전부 다시 설계해야 한다.
- 마을 넷 각각을 독립 좌표계로 두는 지금 구조는 **이미 검증된 자산**이다
  (오버월드 235/235 자가진단, 실기기 확인 이력). 이걸 버리는 건 PLAN
  §1·§44·§49가 반복해서 금지하는 "전체 재작성"에 정확히 해당한다.
- **결론 — 최소 패치로 불가능하다.** 이 프로젝트의 반복된 원칙과 정면
  충돌하므로 권장하지 않는다.

**B안 — 위장된 전환(권장).** 마을마다 독립 좌표계는 그대로 두되, 들길
표식을 순간이동 트리거가 아니라 **"전환 통로"** 진입점으로 바꾼다:
- 들길을 밟으면 그 방향의 테마 있는 좁은 필드 조각(숲길·고갯길·나루터
  등, `field3d.js`의 `chunkAt()`이 이미 그리는 결 그대로, 폭만 좁게)을
  걷게 하고, 이 구간의 반대쪽 끝에 닿으면 그제서야 `travel()`(지금 있는
  순간이동 로직 그대로)을 부른다.
- 이미 있는 인프라를 거의 그대로 재사용한다 — 씨앗 기반 청크 생성
  (`chunkAt`), 마을 로딩 우선순위(`prefetchTownDest`, 이번 세션에서
  이미 만듦, 통로 진입 시점에 미리 부르면 된다), 세이브 스키마(여전히
  "마을 id 하나"로 충분 — 통로 자체는 저장할 상태가 없다, 통로 중간에
  나가면 다시 시작 지점에서 출발해도 무방하다).
- 화면 전환(로딩 화면 없음, 순간이동 없음)이라는 체감만 얻고, 좌표계·
  POI·충돌판정·세이브 구조는 **단 하나도 안 바꾼다** — PLAN §49의
  "기존 기능 재사용 > 최소 수정" 순서를 그대로 지킨다.
- **주의** — 사용자가 말한 "오픈월드"가 반드시 A안(하나의 좌표계)을
  뜻하는 게 아닐 수 있다. "걸어서 이어진다"는 체감이 핵심이라면 B안이
  그 체감을 훨씬 적은 리스크로 준다. A안이 정말 필요하다면(예: 미니맵에
  네 마을을 한 화면의 실제 거리로 보여줘야 하는 등) 그건 이 설계안과
  별도로 사용자에게 다시 확인받을 것.

    통로 표식 자체가 이미 이 반경 언저리(HIGH 기준 지어지는 끝보다도
    조금 더 밖)에 있어, 통로에 아무리 테마를 입혀도 **전부 안개에
    묻혀 하나도 안 보이는** 상태였다. `FIELD_R()` 자체(POI 배치·필드

    있는 마을(`run.corridors` 있음, 넷 다 해당)만 반경을 2칸 더 넓힌다.

    회귀 없음.

    걷힌다. 통로 쪽만 안개를 멀리 밀면 **다른 방향(통로가 없는 쪽)의

    2칸만 균일하게 늘렸다. 통로 어귀 2칸은 목적지 테마로 실제로 보이고,
    그 뒤(남은 2칸)는 지금처럼 안개에 덮인 채로 걷다가 마을에 닿는다 —
    "안개 낀 고갯길·나루" 로 읽어도 어색하지 않은 절충이다. 통로 전체를

### 28-3. 위성↔위성 통로 — 설계안 (Phase 1·2 완료 2026-09-06, 아래 결과 추가)

28-2절이 "위성↔위성 통로는 이 설계안 범위 밖"이라고 적어 둔 자리를
이번엔 실제로 넓힌다. **이 절만으로는 아무것도 안 바뀐다** — 코드는
한 줄도 안 건드렸다.

**좋은 소식 — 인프라가 이미 다 대응한다.** `js/town.js`의 `corridorsFor(cfg)`는
`cfg.exits`(town.js `TOWNS.*.exits` 배열) 하나하나를 그대로 순회해 통로
객체를 만든다 — **한 마을이 통로를 몇 개 갖든 상관없는 구조다**(모루골이
지금도 이미 N·E·S 세 개를 갖고 있다). `js/dungeon.js`의
`corridorReach(ctx,dir)`도 `ctx.corridors` 배열을 매 방향(E/W/S/N)마다
따로 찾아본다 — "마을 하나=통로 하나"라는 가정이 코드 어디에도 없다.
`js/field3d.js`의 `corridorNameAt()`이 돌려주는 테마 키(`'통로:' + co.to`)는
**목적지 마을 id 기준**이라, 위성↔위성 통로를 놔도 이미 있는
`THEME_BIAS['통로:galdae']`·`['통로:jajak']`·`['통로:sogeum']` 표를
그대로 재사용한다 — **새 테마 항목도 필요 없다.** 즉 실제 구현은
**`TOWNS`의 `exits` 배열에 항목 두 줄(왕복) 추가하는 것**에 거의
그친다 — 이 판이 반복해 온 "기존 재사용" 원칙에 이보다 더 맞는
확장은 드물다.

**어느 쌍을 잇나 — 갈대나루(東)↔자작재(北) 하나만, 이번 설계 범위.**
모루골을 중심으로 위성 셋은 정확히 90도씩 벌어져 있다(자작재=N,
갈대나루=E, 소금벌=S, W는 안 쓴다). 세 조합 중:
- **갈대나루-자작재**(E-N, 인접 사분면), **갈대나루-소금벌**(E-S, 인접
  사분면)은 지리적으로 말이 된다 — 모루골을 안 거치고 옆 사분면으로
  바로 질러가는 지름길이다.
- **자작재-소금벌**(N-S)은 **뺀다** — 정반대 방향이라 이 둘을 잇는
  직선은 사실상 모루골 영역을 그대로 관통하게 되고, 그럴 거면 그냥
  모루골을 거치는 것과 다를 게 없어 새 통로의 의미가 없다.
- 갈대나루가 "가까움"(28-1절 마을 설명)이라 첫 지름길의 체감 효과가
  가장 크다고 보고, **갈대나루↔자작재 하나만** 이번 설계 범위로
  잡는다. 갈대나루↔소금벌은 이 설계가 자리 잡은 뒤 같은 방식으로
  한 번 더 반복하면 되는 후속 항목으로 남긴다(억지로 한 번에 다
  뚫지 않는다 — PLAN §1 "작은 단위").

**방향 배정** — 갈대나루는 지금 `exits: [{dir:'W', to:'moru', ...}]`
하나뿐이라 N·E·S가 비어 있다. 자작재는 `exits: [{dir:'S', to:'moru',
...}]` 하나뿐이라 N·E·W가 비어 있다. 모루골 기준 자작재가 북쪽,
갈대나루가 동쪽이니, 갈대나루에서 보면 자작재는 대략 북서쪽, 자작재
에서 보면 갈대나루는 대략 남동쪽이다 — 이 판의 통로는 4방향
(N/E/S/W) 격자로만 표현되므로 정확한 대각선은 못 낸다. 가장 가까운
격자 방향으로 **갈대나루엔 `{dir:'N', to:'jajak', len:CORRIDOR_LEN}`,
자작재엔 `{dir:'E', to:'galdae', len:CORRIDOR_LEN}`**를 왕복으로
단다 — 모루골의 기존 통로들과 똑같이 `CORRIDOR_LEN=4`(800)로
맞춘다(다른 길이를 쓸 이유가 없다).

**모루골 중심 구조와 안 어긋난다** — 28-1절의 "던전 굴혈은 모루골에만
있다"·"위성 셋은 모루골로만 통한다"는 문장은 **모루골이 유일한 던전
접근로**라는 뜻이었지, "위성끼리 왕래가 절대 안 된다"는 규칙이
아니었다(그 문장 자체가 별형 *연결*을 설명한 것이지 *봉쇄*를 정한
게 아니다). 이번 통로는 던전 접근과 무관한, 순수하게 위성 마을끼리
오가는 지름길이라 원래 취지와 상충하지 않는다.

**오버월드(M키) 지도는 안 건드린다** — `js/ui.js`의 `openOverworldMap()`을
실제로 확인했다: 지금 지도는 마을 다섯 칸(hub·N·E·S·W)을 그냥
격자에 앉히기만 할 뿐 **마을 사이에 연결선을 하나도 안 그린다**(코드
전체에 선·경로를 그리는 로직이 없다, `28-1절`이 이미 "텔레포트는
없다 — 보기만 하는 창"이라고 적어 뒀다). 안 그리던 연결을 하나 더
안 그리는 것뿐이라 **이 화면은 위성↔위성 통로가 생겨도 손댈 이유가
없다** — 지도가 "별형"이라는 인상을 준 적 자체가 없다(그냥 마을
다섯 칸을 보여줄 뿐이다).

**위험 요소:**
- **RNG 없음** — `exits` 항목 추가는 순수 데이터라 새 RNG 소비가
  없다. `corridorNameAt()`도 이미 순수 함수다. 28-2절이 반복 겪은
  시드 밀림 함정은 이번엔 해당 사항이 아닐 가능성이 높지만, 자가진단
  항목을 추가한다면 여전히 **파일 맨 끝에 붙이고** 앞선 테스트 상태에
  기대지 말 것.
- **`corridorReach()`의 방향 충돌** — 자작재가 이제 S(→모루골)·
  E(→갈대나루) 두 통로를 동시에 갖는다. `corridorReach(ctx,dir)`는
  방향별로 배열을 훑어 **첫 매치**를 돌려주는데, 한 마을에 같은
  방향(dir)의 통로가 두 개 있으면 안 된다 — 이번 설계처럼 서로 다른
  방향(S와 E)이면 문제없다. **exits 배열에 같은 dir이 중복되지
  않는지 구현 시 반드시 확인할 것.**
- **`prefetchTownDest`/`maybePrefetchCorridor`** — 목적지가 `moru`가
  아닌 통로(갈대나루→자작재)에서도 프리페치가 걸리는지 Phase 2에서
  만든 로직을 그대로 재사용만 하면 될 것 — `co.to`를 이미 범용으로
  쓰고 있어 별도 분기가 필요 없어 보인다, 구현 시 확인만.
- **세이브 스키마** — 28-2절과 동일한 정책(통로엔 세이브 지점 없음)을
  그대로 물려받는다, 새로 정할 것 없음.

### 28-4. 던전도 "걸어서 이어지게" — 설계안 (2026-09-05 작성, Phase 1~4 전부 완료 2026-09-06)

사용자가 "디아블로4처럼 오픈월드가 되고 싶다", "던전을 통해 들어가는 게
식상하다"고 했다. 무엇이 식상한지 짚어보니 셋 다였다: **①** 입구가 마을과
분리된 별도 지점이라는 것 자체, **②** 들어가는 순간의 로딩/장면전환,
**③** 들어가면 방을 치우고 다음 방으로 넘어가는 구조(로그라이크) 자체.
이 절만으로는 아무것도 안 바뀐다 — **코드는 한 줄도 안 건드렸다.**

**먼저 코드로 확인한 사실관계:**

- **던전 입구는 필드가 아니라 마을방 안 고정 좌표다.** 모루골 방 안
  (280,300)의 표식(`town.js:99`)에 `TALK_R` 근접(`touchCheck()`)으로
  닿으면 `ui.js`의 `enterGate()`가 `T.leave()` → `D.enter({floor:1})` →
  `buildFloor()`로 **즉시 재구성**한다(`dungeon.js:561-602`). 로딩
  화면·전환 애니메이션이 없다.
- **방 전환도 똑같은 패턴이다.** `run.room`은 단일 객체(`run.rooms`는
  써지지 않는 죽은 필드)라 방이 여러 개 동시에 존재하지 않는다.
  `goRoom(kind)`(`dungeon.js:632-646`)가 `run.room`을 통째로 새
  `makeRoom()` 결과로 교체하고 플레이어를 `WALL+40`(방 왼쪽 끝)으로
  리셋한다 — 이전 방은 완전히 사라진다. 문 트리거는 **동쪽 벽**
  (`p.x > ROOM_W - WALL - P_R - 4`, `:1855`)에 닿는 것 — 28-2절이
  마을 통로에 쓴 "동쪽 벽 터치" 패턴과 **정확히 같다.**
- **층 전환(`descend()`, `:649-670`)도 같은 메커니즘**(전체 재구성)이고,
  여기에만 은사 선택(`rollBoonChoice()`)이 끼어든다.
- **핵심 밸런스는 방이 아니라 층 단위다.** 은사·정예 확률은 `descend()`
  에서만 걸린다. 다만 `roomIdx`/`roomTotal`은 절차 생성 시드
  (`seedOf(floor,roomIdx,theme)`, `:1124`)와 보스방 판정
  (`isBoss = roomIdx>=roomTotal-1`, `:636`)에 직접 쓰이고, `makeDoors()`
  가 "몇 번째 방인가"라는 순차 진행을 가정한다.
- **던전 입구 GLB는 이미 있지만 이 문과는 무관한 별개 자산이다.**
  `field3d.js`의 `cavemouth`는 필드 먼 고리(ring3)에 서는 순수 장식
  (`FIELD_BLOCK`에 걸리는 막는 소품)일 뿐, 마을방 안 고정 표식과는
  아무 연결이 없다 — 재활용은 가능하지만 지금은 그림만 있고 기능이 없다.
- **`boundPlayer()`가 이미 방-공용 범용 함수다.** 28-2절 Phase 2가 만든
  `ctx.corridors`(방향별 `{dir,extra,lane}`)는 town 전용이 아니라
  `dungeon.js` 자신의 함수 시그니처에 있다 — 실제 던전 런은
  `boundPlayer(p,px0,py0)`를 **ctx 없이** 부르므로(`:1512`,`:1535`)
  지금은 늘 `corridorReach`가 `null`을 돌려줘 예전과 완전히 같다(회귀
  없음). 이 자리에 `run.corridors`를 실어 넘기기만 하면 **똑같은 계산이
  방-방 전환에도 그대로 통한다.**
- **하나 다른 점 — 던전 방의 문은 마을 출구와 달리 "한 벽에 여러 개"다.**
  `makeDoors()`가 동쪽 벽에 2~3개 문을 서로 다른 y에 세로로 늘어놓는다
  (`:497-500`). 마을 통로는 방향(N/E/S/W)당 하나뿐이라 `corridorReach`가
  "방 중심에서 가까운가"(`lane`)만 보면 됐지만, 던전은 **그 문의 y 좌표에
  가까운가**로 기준을 바꿔야 한다 — 문마다 다른 통로를 낼 수 있다는
  뜻이기도 하다(문 종류별로 통로 분위기를 다르게 낼 수 있다).
- **런(`run`)은 세이브에 안 남는다.** `core.save.dungeon`은 최고층·횟수
  같은 메타만 담고, 진행 중인 층·방 자체는 저장 안 된다(로그라이크가
  다 그렇듯 앱을 끄면 그 회차는 사라진다) — 28-2절이 마을 통로에 정한
  "통로엔 세이브 지점 없음" 정책이 던전은 **애초에 적용 대상도 아니다.**
- **`auto.js`의 자동 순회**는 `D.goRoom(pickKind)`를 직접 부른다(`:226`) —
  통로를 걷는 연출 없이 그 자리에서 바로 다음 방으로 넘어가는 지금
  동작을 그대로 유지해야 한다(자동은 눈으로 안 보니 연출이 필요 없다).

**두 갈래를 검토했다 — 마을 오픈월드 때(28-2절)와 같은 A/B 구도다.**

**A안 — 방 개념 자체를 없앤다.** 층 하나를 절차 생성 던전/폐허 하나로
통째로 만들고 그 안을 자유롭게 돌아다니게 한다. 정말로 "열린 던전"이
되지만:
- 시드 체계(`seedOf(floor,roomIdx,...)`)·보스방 판정(`isBoss`)·문 종류별
  분기(`makeDoors`)·은사가 걸리는 "층 답파" 개념 전체를 다시 설계해야
  한다. 몹 스폰·POI·전리품이 지금 "방 하나 = 완결된 인카운터" 단위로
  설계돼 있어, 그걸 하나의 열린 공간에 흩뿌리는 건 밸런스를 처음부터
  다시 잡는 일이다.
- **결론 — 최소 패치로 불가능하다.** 28-2절의 A안이 그랬던 것과 똑같은
  이유(PLAN §1·§44·§49 정면 충돌)로 권장하지 않는다.

**B안 — 위장된 전환, 문마다(권장).** 마을 통로와 똑같은 철학을 방-방
전환에도 그대로 적용한다:
- **던전 입구(①)** — 마을방 안 고정 표식을 없애고, `town.js`의 `exits`
  배열에 **목적지가 다른 마을이 아니라 "던전"인 항목**을 하나 추가한다
  (28-2·28-3절의 `corridorPointRaw`·`corridorLenOf`·`corridorReach`를
  그대로 재사용, 다만 도착 시 `TW.travel()` 대신 `D.enter({floor:1})`을
  부르게 한 줄만 다르다). 통로 자체는 필드의 `cavemouth` 장식을 실제
  기능이 있는 자리로 승격시켜 자연스럽게 감싼다.
- **방 전환(②③)** — 문을 지나는 순간 `goRoom()`을 즉시 부르는 대신,
  그 문의 **y 좌표를 lane 중심으로 삼는 통로 예외**를 `corridorReach()`에
  등록해(방향은 항상 'E' 고정, `lane` 기준만 문마다 다르게) 동쪽 벽
  너머로 짧게(마을 통로보다 짧아도 된다, 예: 1~2 CHUNK) 걸을 수 있게
  열고, 그 통로 반대쪽 끝에 닿으면 그제서야 `goRoom(dr.kind)`가 불린다.
  던전 테마(고분·폐성 등)에 맞는 소품(28-2절 Phase 3의 "테마 가중치 표"
  방식 그대로, 새 소품 없음)을 통로에 입히면, 방을 나설 때마다 "동굴
  샛길을 지나 다음 방에 닿는다"는 체감을 준다 — **③(로그라이크 자체)을
  완전히 없애진 못하지만, ②(뚝 끊기는 전환)는 확실히 없애고 방과 방이
  물리적으로 이어져 있다는 인상을 준다.** 계단문(`stair`)은 이미 있는
  `dg:stairs` GLB로 "내려가는 통로"를 자연스럽게 표현할 수 있다.
- **자동 순회는 통로를 건너뛴다** — `auto.js`가 `goRoom()`을 직접 부르는
  지금 경로는 그대로 둔다(통로는 사람이 걸을 때만 의미가 있는 연출이다).
- **주의** — 사용자가 "방·방 구조까지 다 바꿔본다"고 골랐지만, 코드를
  실제로 읽어 보니 A안(방 개념 완전 소거)은 이 판의 반복된 원칙과

### 28-5. 카메라 각도·화각 — 디아블로 감각 좁히기 (2026-09-06 구현 후 같은 날 되돌림)

**구현했던 것** — 아래 추천안대로 적용했었다: `TILT()` 기본값 0.62→0.4
(부감각 약 47°→62.9°), `PerspectiveCamera` FOV 46°→34°. 던전 쪽
`camAim()` dist 배수도 `tan()` 비율로 다시 계산해(≈1.458) "방이 화면
밖으로 안 나간다"는 불변식은 지켰다. `_test.html` 248/248, `_admin.html
?selftest` 12/12, 정지 화면(마을·던전 각각 하나) 실제 GPU 스크린샷까지
다 통과했었다.

**그런데도 실기기에서 바로 문제가 났다** — 사용자가 실제로 플레이해
보고 "너무 가까워서 몹도 안 보이고... 최악임"이라고 곧바로 지적했다.
**원인 — "방 대각선이 화면에 들어간다"와 "플레이어 주변에서 벌어지는
전투가 다 보인다"는 서로 다른 요구였다.** FOV를 좁히면 dist를 같이
키워도(정지 화면 검증이 확인한 대로 방 자체는 여전히 다 담긴다) 카메라의
**총 화각(수평 포함)이 좁아지는 건 그대로**라 플레이어에서 조금만
떨어진 몹은 화면 밖으로 먼저 밀려난다. 게다가 `tilt`를 낮춘 만큼(더
위에서 내려보게) 카메라가 플레이어 쪽으로 덜 물러나 있어(`back = dist·tl`
이 tilt가 낮을수록 작아진다) 체감상 "바짝 위에서 좁게 내려다본다"는
인상이 커졌다 — 정지 화면 스크린샷 두 장(적이 몇 없거나 가만히 서
있는 장면)으로는 이 문제가 전혀 안 잡혔다.

**교훈 — 이 판처럼 실시간 전투가 핵심인 화면은 정지 화면 스크린샷이나
"방이 다 담기는가"류 기하학적 불변식만으로 카메라를 확정하면 안 된다.**
적이 여럿·플레이어 주변에 흩어진 실제 전투 중 화면으로 검증해야 한다
(다음에 이 절을 다시 시도한다면 `_demo.html#dg`처럼 적이 실제로 움직이는
장면을 실기기에서 직접 보고 판단할 것 — 헤드리스 CDP로도 `DG.dungeon3d.
stats()`나 화면 캡처로 "몹이 몇 마리나 화면에 잡히는지"까지 재는 방법을
먼저 찾아 둘 것).

**되돌린 것** — `TILT()` 0.62, `PerspectiveCamera` FOV 46°, 던전 `camAim()`
dist 배수 1.05로 전부 원래 값으로 되돌렸다(`FOV_DEG`·`DUNGEON_DIST_MUL`
상수는 남겨 뒀다 — 값만 원래대로, 다음에 다시 시도할 자리를 명확히
남기려는 목적). `admin.js` 손잡이 표시값도 0.62로 되돌렸다. `_test.html`
248/248, `_admin.html?selftest` 12/12 재확인.

**하지 않은 것**: 마을/던전 `close` 배수 통일, 캐릭터 모델 텍스처/PBR
재작업, HUD 변경 — 전부 그대로 손 안 댐.

  어둠만 찍힌" 실패를 이미 겪었다, 2026-09-01). 던전은 벽으로 막힌
  방이라 꼭 다 담아야 하고, 마을/필드는 열린 땅이라 잘려도 괜찮다 —
  **이 차이 자체는 건드리지 않는다.** FOV를 좁히면 같은 dist로는 방이
  화면 밖으로 나가므로, FOV를 좁히는 만큼 dist 배수도 같이 올려 "방이
  다 담긴다"는 불변식을 지켜야 한다(공식: 화면에 담기는 폭 ∝
  dist·tan(fov/2) — FOV가 작아지면 그만큼 dist를 키워 보정. 정확한
  배수는 손으로 굴리지 말고 코드에 상수로 남겨 계산할 것).

**추천 — 작은 단위, 실측 위주:**
```
1. TILT() 기본값(dg3d.tilt, 0.62)을 낮춘다 — 부감각을 60°대로 올리려면
   tl≈0.35~0.45 범위(위 공식으로 원하는 각도에서 역산할 것, PLAN §16
   "너무 위에서 내려보지 말 것"도 같이 지킬 것 — 90°에 너무 가깝지
   않게).
2. PerspectiveCamera FOV(46)를 32~36° 안팎으로 좁힌다.
3. FOV를 좁힌 만큼 camAim()의 던전 쪽 dist 배수(1.05)만 위 공식으로
   다시 계산해 방이 여전히 다 담기게 맞춘다(마을 쪽 0.4는 그대로).
4. 한 번에 확정하지 말고 실제 GPU 스크린샷으로 반복 조정한다 —
   **헤드리스 SwiftShader는 이 판 3D 조명·톤매핑을 못 믿는다**
   (2026-09-06 확인, 아래 "검증" 참고). `--no-first-run` 플래그로 실제
   창을 띄우고 PowerShell `System.Drawing.Graphics.CopyFromScreen()`로
   캡처하는 방식을 쓸 것 — 헤드리스 `--screenshot`이 아니다.
5. `_test.html`의 camAim() 관련 항목(`3D — 회전이 없다`, `3D — 줌과
   기울기가 듣는다` 등)이 새 기본값에서도 통과하는지 확인 — 로직이
   아니라 하드코딩된 각도 가정이 있으면 그 항목의 기준값만 새 기본에
   맞춰 갱신한다(항목 수를 늘리거나 줄이지 않는다).
```

**하지 않을 것**: 마을/던전 `close` 배수를 "통일"하려는 시도(의도된
차이다, 건드리면 옛 "화면이 어둠만 찍힌다" 버그가 되돌아온다) · 캐릭터
모델 텍스처/PBR 재작업 · HUD/아이콘 변경(감사 결과 이미 디아블로에
가깝다).

**검증** — `_test.html` 3회(새 프로필마다) 완전 동일, `_admin.html?selftest`
n/n, 그리고 **실제 GPU 스크린샷**(마을 `#camp`·던전 `#dg` 둘 다)으로
방이 화면 밖으로 안 나가면서 더 위에서 내려다보는 각도로 바뀐 것을
직접 확인 — 조정 전/후를 나란히 비교해 사용자에게도 보여줄 것.

### 28-6. 지형 높낮이 버그 — 액터가 늘 y=0 에 그려짐 (2026-09-06 발견·수정)

사용자가 §28-5 되돌림 직후 실기기 플레이 중 두 가지를 연달아 지적했다:
"마을 밖 바닥이 높낮이가 달라서 캐릭터가 다 가려지고 화면이 못따라가
캐릭터가안보임", "벽구조가 아니고 다 뚫고 감". 코드로 확인하니 **둘 다
같은 원인**이었다.

**원인** — `field3d.js`의 `heightAt()`가 방 밖 들판에 언덕·비탈(기복)을
주고, 땅 타일(`buildField()`)과 정적 자연물(나무·바위)은 이미 그 값을
쓰고 있었다. 그런데 **나(`me.node`)·적(`a.node`)·카메라(`camAim()`)는
전부 y=0 을 그대로 쓰고 있었다** — 플레이어가 언덕에 올라서도 몸도
카메라도 그대로 y=0 에 머물러, 캐릭터가 솟은 땅에 파묻힌 것처럼 가려지고
(제보 1), 동시에 그게 마치 아무 저항 없이 언덕 속으로 들어가는 것처럼
보였다(제보 2 — 충돌 판정 자체는 원래도 지형 기복과 무관하고 개별
장식물(FIELD_BLOCK)만 막는데, 그 사실이 "벽처럼 안 막힌다"가 아니라
"땅 밑으로 꺼진다"는 시각적 버그와 겹쳐 더 두드러졌다).

**고친 것** — `dungeon3d.js`:
- `camAim()`에 `groundY` 인자를 추가해 `pos.y`·`look.y` 둘 다에 더한다
  (방 안에서는 늘 0이라 회귀 없음).
- `render()`에 `groundYAt(x,z)` 헬퍼를 두고(`buildField()`와 **정확히
  같은 seed 산식**을 써야 그림과 액터가 같은 높이를 본다) 나·적·횃불의
  Y좌표와 `camAim()` 호출에 이 값을 먹인다.

**검증** — `_test.html` 헤드리스 3회 `RESULT 248/248` 완전 동일,
`_admin.html?selftest` `ADMIN 12/12`(camAim 시그니처에 인자를 추가만
했고 기존 호출은 그대로라 회귀 없음). 실기기 확인은 다음 세션 몫으로
남는다 — 사용자에게 직접 플레이해서 확인해 달라고 요청할 것.

**하지 않은 것** — 지형 기복 자체에 새 충돌(가파른 비탈을 벽처럼 막는
것)을 추가하지 않았다. 위 진단대로 "다 뚫고 감" 제보의 상당 부분이
Y좌표 버그 때문이었을 가능성이 높아, 우선 이것만 고치고 실기기에서도
여전히 뚫린다는 재확인이 오면 그때 별도 절로 설계할 것(경사도 기준을
새로 정해야 하는 더 큰 결정이라 섣불리 먼저 손대지 않았다).

### 28-7. 마을 확장 — 치수·콘텐츠 둘 다 (2026-09-06)

사용자가 "마을이 넘 작아"라고 지적했고, 되물어 "둘 다(치수+콘텐츠)"를
원한다고 답했다. 동시에 이 판의 장기 방향을 "디아블로류 오픈월드 +
여러 ARPG의 좋은 점을 최대한 반영"으로 못박았다(자세한 내용은 auto
memory `saga_dungeon_arpg_vision`에 기록 — 다음 세션도 그 파일을
참고할 것).

**치수** — `town.js`의 `BASE_W`/`BASE_H`(560×380) 자체는 건드리지
않았다. 그 위 주석(2026-08-30)이 이미 겪은 함정이 있다 — 아이소메트릭
마름모의 가로세로비(1.83:1)가 고정이라 폰 세로 화면은 늘 가로가
병목이고, 방을 키우면 그 병목에 맞춰 화면 전체가 축소돼 사람이
개미만 해진다(그래서 이미 한 번 720×460을 시도했다가 되돌린 적 있다).
**`DESK_SCALE`(데스크톱 전용 배율, `wideDesktop()`이 참일 때만 적용)만
1.4→1.7로 올렸다** — 폰은 `BASE_W`/`BASE_H` 그대로 쓰므로 회귀가 없다.

**콘텐츠** — 네 마을 전부에 집을 하나씩 더 얹었다(모루골 4번째 집,
위성 마을 셋은 각자 2번째 집). 좌표는 기존 소품·NPC·스폰 지점에서
전부 100 유닛 이상 떨어진 자리로 손으로 계산해 골랐다 — 벨타워가
스폰(195,240)에서 겨우 60 떨어져 있어 "화면이 온통 돌벽"으로 보였던
함정(§28-4 이전 기록)을 되풀이하지 않으려 거리부터 쟀다. 건물은 전부
기존에 이미 구현된 종류(`house`)만 재사용했다 — 새 GLB·새 렌더 코드
없음.

**검증** — `_test.html` 헤드리스 3회 `RESULT 248/248` 완전 동일,
`_admin.html?selftest` `ADMIN 12/12`(둘 다 좌표 데이터만 바뀌어 로직
영향 없음). 실제 GPU 스크린샷으로 모루골 스폰 지점·새 집(430,150) 근방
둘 다 확인 — 카메라가 벽에 박히는 등의 이상 없음.

**후속(2026-09-06, 이어서)** — 위성 마을 셋의 새 집도 CDP 스크린샷으로
확인했다. `DG.town._reset(townId)`/`_put(x,y)`(자가진단용으로 이미 있던
API)로 순간이동한 뒤 GPU 스크린샷을 찍는 `_cdp_town_shot.py`를 새로
만들었다(`_cdp_shot.py`의 WS 클래스 재사용, 첫 실행이면 이름 입력 화면도
자동으로 통과시킨다). 갈대나루(420,250)·자작재(450,300)·소금벌(420,300)
셋 다 인물이 정상 렌더되고 문 앞 시야가 트여 있다 — §28-4 이전에 겪었던
"화면이 온통 돌벽" 함정 없음. **실기기 확인은 여전히 남아 있다**(이건
헤드리스·소프트웨어 렌더 기준).

**하지 않은 것** — NPC를 늘리지 않았다(새 직군·시트·대사가 필요한
더 큰 결정이라). 마을 간 "통일된 큰 좌표계"(§28-2 A안, 이미 반려)도
다시 꺼내지 않았다 — 지금 위장된 전환 구조는 그대로 두고 각 마을
내부만 키웠다.

### 28-8. 진짜로 이어진 오픈월드(A안) — 마을 규모를 세계 단위로 (2026-09-06,
Phase 1~4 완료, 이어지는 세션)

바로 위 §28-7이 "A안은 이미 반려"라고 적은 지 몇 시간 만에 뒤집혔다 —
같은 날 이어진 대화에서 사용자가 마을을 "100개여도 됨" · "전세계 기준"
규모로 늘리고 싶다고 했고, 그 과정에서 지금 미니맵이 "점만 보인다"는
지적과 "이렇게 봐서는 디아블로처럼 이동도 어렵겠다"는 지적이 나왔다.
코드로 확인해 설명한 결과 — 두 불만은 같은 뿌리(마을·던전이 각각 독립
좌표 공간이고, "통로"는 §28-2·§28-4가 고른 위장 전환일 뿐 실제로 이어진
공간이 아니다)였고, 사용자가 **"그렇다, 진짜 이어진 세계(A안)로 간다"**고
명시적으로 확답해 이 절이 시작됐다. 여러 세션짜리 대공사라는 점도
동의됐다 — §28-2/§28-4가 A안을 반려한 건 "마을 4개" 규모 기준이었고,
지금은 그 전제 자체가 달라졌다.

**던전 내부는 범위 밖이다** — 디아블로4도 마을+필드는 이어진 하나의
공간이지만 던전 내부는 별도 인스턴스다. 이 판도 같다: `run.room`(단일
객체)·`makeRoom()`(RNG 몹/전리품)·`seedOf`/`THEMES` 등 던전 층 내부는
전혀 안 건드렸다 — 마을↔필드↔다른 마을 축만 바꿨다.

**Phase 1 — 세계 좌표 뼈대. 완료.**

- **`js/dungeon.js`** — `inRoomRect`·`fieldBlockedAt`·`boundPlayer`
  셋에 `ctx.anchor{x,y}`(이 방의 로컬 원점이 서 있는 세계 좌표, 없으면
  0,0 — 옛 동작과 완전히 같다)와 `ctx.noRoom`(방 사각형 자체가 없는
  열린 들판 — 세계 한계(`WORLD_LIMIT=60000`)만 두고 소품 충돌만
  축분리로 본다) 지원을 더했다. `spawnFieldEncounters`도 같은 이유로
  anchor 오프셋을 반영했다. **anchor·noRoom 이 없으면 전부 예전과
  100% 같다** — 던전 방은 이 필드를 안 넘기므로 회귀 없음.
- **`js/town.js`** — 가장 큰 변경.
  - `WORLD_ANCHOR`(모루골 원점, 나머지 위성 셋은 `ANCHOR_DIST=4800`
    (=24×CHUNK) 간격으로 exits 방향 그대로 배치) + `anchorOf`·
    `footprintDist`·`pickActiveTown`·`nearestTownId`를 새로 뒀다.
    간격은 마을 발판+필드 반경을 다 합쳐도 안 겹칠 만큼 넉넉하다(자가
    진단이 확인).
  - **은퇴시킨 것** — `travel()`(들길을 밟으면 순간이동+전체 재구성),
    `corridorPointRaw`/`corridorPoint`/`corridorLenOf`/`corridorsFor`
    (§28-2·§28-3이 쌓은 "위장 통로 결" 클램프 예외 표), `builtFieldR`
    (그 표 전용 AUTO 함정 방지값), `CORRIDOR_LEN`/`LANE`/`SAFETY`.
    이제 마을 사이는 진짜로 걸어서 건너간다 — "들길을 밟으면" 트리거
    자체가 필요 없다.
  - `build()`가 이제 CURRENT_TOWN이 가리키는 마을을 **그 앵커 세계
    좌표**에 짓는다(decor·npc·마크 전부 앵커 오프셋을 더함) — 플레이어
    위치는 안 건드린다(옛 코드는 매번 로컬 스폰 좌표로 되돌렸다).
    CURRENT_TOWN이 null(들판, 활성 마을 없음)이면 장식·NPC·마크 없는
    빈 방을 둔다.
  - `update()`가 매 틱 `pickActiveTown(player.x,player.y)`으로 활성
    마을을 다시 구하고, 바뀌었을 때만 `build()`+세이브(`saveWorldPos`+
    `core.persist()`, 옛 travel()이 마을을 건널 때마다 저장하던 것과
    같은 빈도)를 건다 — 매 틱 다시 짓거나 저장하지 않는다.
  - **exits 데이터는 안 지웠다** — "어느 마을이 어느 마을과 이웃인가"는
    여전히 유효한 정보이고(오버월드 지도·Phase 2가 쓸 자리), 다만 마을로
    건너가는 마크(`exit_<townId>`)는 더는 안 세운다(발동 트리거가 필요
    없어져서) — 남는 건 `exit_dungeon`(굴혈, 여전히 실제 트리거) 하나뿐.
  - **세이브 스키마** — `core.save.town`이 `{current}`에서 `{current,
    pos:{x,y}}`로 바뀌었다(`core.js`). `pos`가 없으면(옛 세이브) `enter()`
    가 `current`의 마을 앵커 스폰으로 한 번 마이그레이션한다 — 진행
    손실 없음(자가진단이 확인).
- **`js/ui.js`** — `town:mark` 핸들러에서 `exit_*` → `T.travel()` 가지를
  뺐다(이제 그런 마크 자체가 안 선다, 죽은 코드 제거).
- **`js/dungeon3d.js`** — `maybePrefetchCorridor`의 주석만 갱신(§28-2
  Phase 4의 "이웃 마을 자산 미리 당기기"가 지금은 아무 마을 exit_* 에도
  안 걸린다는 사실 기록, 코드는 안 지웠다) — **알려진 한계**로 아래에 남김.

**검증** — `_test.html` **259/259** 3회 완전 동일(옛 corridor 전용 항목
여섯을 새 항목(세계 앵커 간격·exits 데이터 무결성·경계를 걸어서 넘으면
순간이동 없이 활성 마을이 갈림·세계 좌표 세이브·옛 세이브 마이그레이션)
으로 교체), `_admin.html?selftest` **ADMIN 12/12**, 실제 페이지
콘솔 에러 0. "순간이동 없음" 검증은 `_put()`으로 좌표를 조금씩 옮기며

# 51. 동행(同行) — 부대 2번째 인물이 용병처럼 곁에서 싸운다 (2026-09-06)

사용자가 명시적으로 요청했다: "동료도 따라 다니면서 같이 싸우던지 용병처럼."
같은 대화에서 "그래픽을 이정도만 가능하면 게임이라도 재미 있어야지"라고도
했다 — 그래픽보다 게임성(콘텐츠·체감)을 우선한다는 방향과 같은 맥락이다.

**왜 이게 새 기능이었나** — `hero.js`의 `partyPower()`(부대 전원의 공격력·
방어력 합산)가 이미 `dungeon.js`의 `atkOf()`/`hpMaxOf()`에 그대로 들어간다.
즉 부대 2번째·3번째 인물은 이미 선두의 수치에 **녹아 들어가 있었다** —
화면에 안 보일 뿐 전투력엔 기여하고 있었다. 그런데 눈에 안 보이니
"동료가 안 움직인다"로 느껴졌다.

**어떻게 짰나 — 기존 분신(summon) 메커니즘을 그대로 빌렸다.**
`dungeon.js`에 이미 방사(方士)의 소환 스킬이 쓰는 `summon()`/`updateMinions()`
가 있다 — "가장 가까운 적을 쫓다가 사거리 안이면 때리고, 없으면 주인
곁으로 붙는다"는 AI를 이미 검증된 채로 갖고 있었다. 동행은 그 패턴을
그대로 따르되 **시간제한이 없고**(분신은 `t`가 다하면 사라진다), **부대
2번째 인물의 정체성**(id·생김새·장착 무기)을 그대로 입는다.

- `companionHeroId()` — `core.save.party[1]`. 부대가 하나뿐이면 없다.
- `spawnCompanion()` — 층에 들어갈 때(`buildFloor()`)만 다시 잡는다.
  `run.player`와 같은 주기 — 방을 넘어갈 때(`goRoom()`)는 좌표만
  선두 곁으로 다시 둔다.
- `updateCompanion(dt)` — `updateMinions()`와 같은 결의 AI(쫓다·때리다·
  돌아오다). `update()` 안에서 `updateMinions(dt)` 바로 다음에 부른다.
- **때림 배율** — `atkOf()`(부대 합산, 이미 2번째 인물 몫이 들어 있다)를
  다시 쓰지 않는다. `hero.power(id)`(개인 전투력, 부대 합산과 별도 식)로
  선두 대비 제 몫을 새로 매기고(0.2~1.5배 클램프) **덤이라는 뜻으로 0.55를
  곱한다**(`companionMul()`). 그래서 부대 합산 수치의 균형은 하나도 안
  건드리면서, 2번째 인물을 키우면 그 덤이 실제로 세진다.
- **적이 동행을 때리지 않는다** — 분신과 같은 결정이다. 체력·죽음·부활을
  새로 만들면 판이 훨씬 커진다(하드코어 모드의 "한 번 죽으면 끝" 규칙과도
  얽힌다). "용병처럼 같이 싸운다"는 뜻은 살리되, 판정을 최소로 늘렸다.

**화면(3D만, 2D는 아직)** — `dungeon3d.js`에 `kind:'ally'` 배우 하나를
더했다. 'me'(선두)와 완전히 같은 조립(`AS3.buildHero` + `attachWeapon`)
이지만 seed를 `'ally:'+그 인물 id`로 박아 선두와 다른 생김새 조합이
나온다(`'npc:'+key`와 같은 요령). 장착 무기도 그 인물이 실제로 낀 것을
읽는다(`weaponLookOf(id)` — 예전엔 `meWeaponLook()`이 `party[0]`만 봤다).
CDP로 실제 던전 런에서 확인 — 초록빛 인물이 선두 곁에 서고, 근처 적에게
다가가 실제로 베어 피해 숫자가 뜬다.

**남은 것 — 2D 화면(`dungeon-view.js`)에는 아직 안 그린다.** 이 판의 3D가
꺼지는 자리(WebGL 미지원 등)에서는 동행이 눈에 안 보인다(전투 자체엔
계속 참여한다 — 판정은 화면과 갈라져 있다). 다음에 2D도 채울 것.
NPC 늘리기(§28-7 뒤 §29 근방)처럼 부대 3번째·4번째까지 다 세우는 것도
검토할 수 있으나, 화면이 좁은 폰에서 인물이 너무 많아지는 문제가 있어
우선 2번째 하나로 시작했다.

**검증** — `_test.html`에 동행 전용 항목 넷(있음·없음·배율 범위·실제
타격)을 추가, 헤드리스 3회 `RESULT 256/256` 완전 동일. `_admin.html?
selftest` `ADMIN 12/12`. `_demo.html#dg`(4인 부대)를 CDP로 띄워 실시간
루프에서 동행이 적 옆에 서서 베고(피해 숫자 27 등 실측) 있는 것을
스크린샷으로 확인했다.

# 52. 마을 경비 · 전체 지도(자동지도) — 사용자 실기기 제보 둘 (2026-09-06)

**① "마을 아직도 몹들이 들어오네 경비가 없나?"** — 들판 로머(`.field`)가
넉백(`strike()`의 knockback)에 맞아 마을 안으로 들어오던 버그. 원래
"들판 로머는 방 벽 좌표로 clamp 안 한다"는 규칙이 있었는데(예전에
`core.clamp(..., WALL+e.r, ROOM_W-WALL-e.r)`를 그대로 썼다가 맞을 때마다
방 안으로 순간이동하는 버그를 먼저 겪어서 아예 clamp를 뺐다) — 그런데
그 대신 **아예 안 막아서**, 플레이어가 로머보다 마을 바깥쪽에 서서
때리면 넉백 방향(플레이어 반대쪽)이 마을 쪽을 가리켜 벽을 그대로
뚫었다. `stepFieldCombat`의 이동 clamp("축을 나눠 막아 대각선으로
다가와도 한쪽 축은 계속 미끄러진다")와 **같은 요령**으로 고쳤다 —
방 안쪽으로 들어가는 축만 한쪽씩 막는다(`inRoomRect(kx, e.y, run)` 등).
새 clamp가 아니라 이미 검증된 요령을 넉백에도 마저 적용한 것뿐이다.

**② "M키 지도가 점만 보여" → "디아블로처럼·투명으로 보여 줄 수도 있고"**
— 예전 M키(🧭 오버월드)는 마을 넷을 고정된 3×3 상자 그림(이름만)으로
보여 줬다. 그 대신 **미니맵(minimap.js)의 blips()·norm()을 그대로
재사용해 화면 전체를 반투명하게 덮는 큰 판**으로 갈아 끼웠다 — 새
좌표계를 만들지 않는다. 마을·던전 어디서나 켜진다(디아블로의 자동지도도
마을 전용이 아니다). 마을에서는 들길(exit_*) 옆에 그 마을 이름을
바로 적어(예: "들길 — 자작재 방면") 예전 오버월드 창이 하던 일(어느
방향에 어떤 마을이 있는지)까지 한 화면에 합쳤다. `ui.js`의
`openOverworldMap`/`toggleOverworldMap`은 이름은 그대로 두고 속을
`DG.minimap.openBig()`/`toggleBig()` 위임으로 바꿨다 — 안 쓰는
`.ow-grid`/`.ow-cell` CSS와 `#encounter` 카드 방식은 지웠다.
`_demo.html`에 빠져 있던 `minimap.js` 스크립트도 이 김에 더했다
(index.html과 스크립트 목록이 어긋나 있던 것 — 그전엔 M키를 그 파일에서
안 눌러 봐서 안 드러났다).

**검증** — `_test.html`에 전체지도 전용 항목 셋(비율 계산·켜짐/꺼짐·
토글) 추가, 헤드리스 3회 `RESULT 259/259` 완전 동일. `_admin.html?
selftest` `ADMIN 12/12`. `_demo.html#dg`를 CDP로 띄워 던전 방·마을
둘 다에서 `DG.minimap.openBig()`를 직접 불러 스크린샷 확인 — 던전은
방 벽·적·나 점이, 마을은 들길 셋(자작재·갈대나루·소금벌 방면)이 이름과
함께 실제로 뜬다.

**남은 것** — 마을 경비 고침은 코드로만 확인했다(자가진단은 실제 넉백을
쏘아 보지 않는다 — `strike()`가 `boonVal`·`fx`처럼 화면 연출까지
같이 건드려서 진단이 값만 흉내 내긴 까다롭다). 다음에 실기기에서 몹을
벽 쪽으로 여러 번 때려 실제로 안 들어오는지 봐 줄 것. 전체지도의 텍스트
라벨이 화면 맨 아래("탭하면 닫힙니다")와 겹칠 수 있다(마을에 따라 들길이
바닥 쪽에 있으면) — 사소한 겹침이라 이번엔 안 건드렸다.

# Claude Code 실행 지침

지금 바로 코드를 수정하기 전에 먼저 프로젝트 구조를 분석한다.

전체 프로젝트를 한꺼번에 읽지 말고 entry point와 핵심 파일부터 찾는다.

그 다음 현재 기능 중 재사용 가능한 부분을 판단한다.

그리고 Phase 1부터 순서대로 진행한다.

각 Phase마다 실제 코드를 수정하고 검증한다.

**가장 중요한 것은 토큰 절약이다.**

불필요한 파일을 읽거나 전체 코드를 반복 출력하지 않는다.

작업 중 이미 확인한 파일은 다시 전체를 읽지 않는다.

변경이 필요한 부분만 읽고 수정한다.

작업 결과를 장황하게 설명하지 말고 실제 구현에 집중한다.

단, 중요한 구조 변경이나 에셋 추가가 필요한 경우에는 짧게 이유만 기록한다.

최종 목표는 기존 `saga-dungeon`의 게임 시스템을 버리는 것이 아니라,

**기존 시스템 + 실제 3D 에셋 + 넓은 필드 + 다양한 환경 + 랜덤 콘텐츠 + 모바일 세로/가로 지원 + 고품질 액션 전투**

를 결합하여 완전히 새로운 수준의 SAGA-DUNGEON으로 만드는 것이다.

# 부록 · 코드로 그리지 말고 에셋으로 (다섯 판 공통 방침)

**사용자 지시 (2026-08-28). 다섯 판에 다 같이 적용한다.**

> "스크립트로 쓰고 있는 것들은 다 에셋으로 변경 했으면 해."
> "스크립트는 오직 이벤트나 기능들."
> "도감 일러스트나 캐릭터들도 에셋이 없는지 확인해주고 추가해줘. UI 도."

즉 **코드가 도형·그림을 조립해 만들던 것은 전부 실제 에셋으로 갈아 끼운다.**
3D 모델만이 아니다 — **도감 일러스트 · 인물 초상 · UI 그림**까지 포함한다.
남는 스크립트는 **이벤트와 기능(판정 · 규칙 · 상태)** 뿐이다.

## 왜

사용자가 먼저 고른 것이 **품질**이다. "스크립트로 그려서 퀄리티가 떨어진다 —
에셋을 써라" 가 이 축의 시작이었고, 받을 수 있는 CC0 에셋이 이 판의 결
(한옥 · 갓 · 도포)과 다르다는 것을 알고도 **"둘 다 얹는다(품질 우선)"** 를 골랐다.
그러니 **"결이 안 맞아서" 는 안 하는 이유가 되지 못한다.**

## 어떻게

- 새 작업을 잡을 때 **그 판에서 아직 코드가 그리는 것부터 센다.**
  3D 소품 · 건물 · 인물뿐 아니라 **캔버스로 그리는 초상 · 카드 · 아이콘**까지
- **되돌림 길은 지우지 말고 손잡이로 남긴다.** 에셋을 못 받는 자리가 실제로 있다 —
  `file://` 단독판 · 낮은 품질 등급 · 오프라인. 그때는 조용히 옛 그림으로 돌아간다
- **에셋을 못 구하면 그 사실을 알린다.** 이 망은 GitHub(`raw.githubusercontent.com` ·
  `api.github.com`)만 열려서 미러에 없는 것은 못 받는다. CC0 로 존재하지 않는 것
  (예: 특정 인물 일흔의 초상)은 **"안 한다" 가 아니라 "이래서 막혔고 대신 이것을
  할 수 있다"** 로 보고한다 — 사용자가 직접 받아다 줄 수도 있다
- 출처와 라이선스는 판마다 `assets/ASSET_LICENSES.md` 에 적는다.
  **공개 저장소라 재배포가 안 되는 것은 애초에 받지 않는다.**
  저작자 표시가 필수인 것(CC-BY)은 표시 문구를 같이 옮긴다
- **원작사의 실제 에셋은 넣지 않는다.** 이 규칙은 그대로다
