# SAGA-STORY Godot 4 3D 전환 작업지시서

## 0. 최우선 원칙

이 프로젝트는 기존 `saga-story`를 기반으로 Godot 4 게임으로 전환한다.

최우선 순위는 다음과 같다.

1. **토큰 사용량 최소화**
2. 기존 기능 최대한 보존
3. Godot 4 기반으로 재구축
4. 3D 게임으로 전환
5. 모바일 세로/가로 화면 모두 지원
6. 실제 게임처럼 보이는 그래픽과 연출
7. 과도한 시스템/코드 생성 금지
8. 기존 기능을 분석하지 않고 무작정 새로 만들지 말 것

# 5. 3D 전환 방향

단순히 2D 이미지를 3D 공간에 배치하는 방식은 사용하지 않는다.

실제 3D 게임처럼 구성한다.

## 기본 카메라

쿼터뷰 / 액션 RPG 스타일을 기본으로 한다.

```text
        Camera
           \
            \
             Player
          /    |    \
      Enemy  Enemy  Enemy
```

카메라는 플레이어를 따라간다.

기본적으로:

- 약간 높은 시점
- 3/4 방향
- 플레이어 중심
- 부드러운 카메라 이동
- 전투 시 적이 잘 보이는 거리

---

# 6. 플레이어

Player는 실제 3D CharacterBody3D 기반으로 만든다.

예:

```text
Player
 ├─ CharacterBody3D
 ├─ CollisionShape3D
 ├─ Visual
 │   └─ Model
 ├─ AnimationPlayer / AnimationTree
 ├─ CameraTarget
 ├─ Weapon
 └─ Effects
```

필수 기능:

- 이동
- 달리기
- 방향 전환
- 기본 공격
- 스킬
- 피격
- 사망
- HP
- MP 또는 스킬 자원
- 경험치
- 레벨업

---

# 7. 전투

saga-story의 핵심 재미는 사냥/전투가 되도록 강화한다.

단순히 적을 클릭하는 방식이 아니라
실제 3D 액션 RPG 느낌을 목표로 한다.

## 기본 공격

- 공격 모션
- 공격 범위
- 히트 판정
- 데미지
- 피격 효과
- HP 감소
- 적 사망

## 스킬

최소 3종 이상 구조를 만든다.

예:

- 기본 공격
- 강공격
- 범위 공격

스킬 시스템은 데이터 기반으로 만든다.

---

# 8. 적

Enemy도 3D CharacterBody3D 기반으로 만든다.

필수:

- 플레이어 감지
- 추적
- 공격
- 피격
- 사망
- 드랍

적 종류를 최소 3개 이상 지원할 수 있는 구조로 만든다.

예:

```text
슬라임
늑대
도적
```

실제 에셋이 없으면 임시 저폴리 모델을 사용하되,
구조 자체는 추후 GLB/GLTF 에셋으로 쉽게 교체할 수 있도록 한다.

# 9. 3D 맵

현재 게임보다 훨씬 넓고 풍부하게 보이도록 만든다.

단순한 평면 하나만 사용하는 것을 금지한다.

최소 구성:

- 지형
- 길
- 언덕
- 나무
- 바위
- 풀
- 건물
- 장식물
- NPC 위치
- 사냥터
- 포탈/출입구
- 배경 구조물

플레이어가 이동할 때
"빈 맵"이라는 느낌이 들지 않도록 한다.

# 10. 맵 디자인

맵은 한 화면에 모든 것을 보여주는 방식이 아니라
탐험 공간처럼 구성한다.

예:

```text
        [숲]
          |
[마을]--[초원]--[동굴]
          |
       [폐허]
```

각 지역마다 분위기를 다르게 한다.

---

# 11. 그래픽

목표는 AAA 그래픽이 아니다.

**모바일에서 실행 가능한 고품질 스타일리시 3D RPG**를 목표로 한다.

우선순위:

1. 캐릭터 실루엣
2. 지형
3. 조명
4. 그림자
5. 환경 오브젝트
6. 이펙트
7. UI

에셋을 사용할 수 있도록 구조를 만들고,
GLB/GLTF 모델 교체가 쉽도록 한다.

---

# 12. 에셋 전략

모든 3D 모델을 코드로 생성하지 않는다.

다음 구조를 사용한다.

```text
assets/
 ├─ characters/
 ├─ enemies/
 ├─ environment/
 ├─ weapons/
 └─ effects/
```

실제 GLB/GLTF 에셋이 있으면 우선 사용한다.

없는 경우:

- 저폴리 임시 모델
- 기본 Godot Mesh
- 단순 Material

등으로 프로토타입을 완성한다.

중요:

**에셋이 없다는 이유로 개발을 중단하지 않는다.**

---

# 13. 모바일 최적화

모바일을 중요한 플랫폼으로 취급한다.

다음 원칙을 적용한다.

- 불필요한 실시간 조명 최소화
- 그림자 최소화
- LOD 적용
- 화면 밖 오브젝트 비활성화
- 적 수 제한
- 이펙트 제한
- 텍스처 크기 관리
- 반복 오브젝트 인스턴싱
- MultiMesh 활용 검토
- 오브젝트 풀링

Godot의 3D 최적화 방식에 맞춰
보이는 것보다 실제 성능을 우선한다.

---

# 14. 렌더러

모바일 중심이므로 Godot의 Mobile 렌더러를 우선 검토한다.

다만 웹 배포가 필요할 경우
Compatibility 렌더러도 고려한다.

최종 선택은 다음 기준으로 한다.

```text
모바일 앱 중심
→ Mobile Renderer

웹 실행 중요
→ Compatibility Renderer

PC 고품질 중심
→ Forward+
```

현재 목표는 모바일 게임이므로
불필요하게 Forward+를 강제하지 않는다.

```text
│          │
│  PLAYER  │
│          │
│ joystick │
│   skills │
└──────────┘
```

가로:

```text

│ HUD                │
│                    │
│       PLAYER       │
│                    │
│ joystick     skill │

```

# 30. 충돌

Godot 물리 시스템을 사용한다.

플레이어:

```text
CharacterBody3D
CollisionShape3D
```

적:

```text
CharacterBody3D
CollisionShape3D
```

공격 판정은 별도의 Area3D 또는 RayCast3D 등을 사용한다.

---

# 31. 코드 구조

가능하면 다음처럼 단순하게 유지한다.

```text

SaveManager
PlayerController
EnemyController
CombatSystem
InventorySystem
EquipmentSystem
SkillSystem
```

반대로 기능별 스크립트를 지나치게 잘게 쪼개지도 않는다.

# 34. 중요한 개발 방식

각 Phase가 끝날 때 반드시 실행 가능한 상태여야 한다.

예:

```text
Phase 1 완료
→ 실행 가능

Phase 2 완료
→ 캐릭터가 실제로 이동

Phase 3 완료
→ 몬스터가 플레이어를 추적

Phase 4 완료
→ 실제 전투 가능
```

한 번에 모든 기능을 만들지 않는다.

# 39. 최종 품질 목표

기존 웹 게임을 단순히 Godot으로 옮기는 것이 목표가 아니다.

최종적으로는:

**"모바일에서 플레이할 수 있는 스타일리시 3D 액션 RPG"**

느낌이 나야 한다.

특히 기존 saga-story의 가장 큰 문제인

- 좁고 단순한 공간
- 부족한 지형지물
- 단조로운 전투
- 낮은 시각적 밀도

를 개선한다.

플레이어가 게임에 들어갔을 때
"웹페이지"가 아니라
"3D 게임"이라고 느껴야 한다.

---

# 40. 토큰 절약 최종 규칙

Claude Code는 다음 순서만 따른다.

```text
ANALYZE
↓
PLAN
↓
IMPLEMENT
↓
TEST
↓
FIX
```

매 단계마다 필요한 파일만 확인한다.

이미 확인한 내용은 다시 읽지 않는다.

기존 코드가 재사용 가능하면 재사용한다.

새로운 시스템을 만들기 전에
기존 시스템으로 해결할 수 있는지 먼저 확인한다.

**토큰보다 가치가 낮은 코드는 만들지 않는다.**

---

# 41. 최초 실행 명령

Claude Code를 실행한 뒤 다음 작업부터 시작한다.

```text
1. 현재 프로젝트 구조 분석
2. saga-story 핵심 기능 분석
3. Godot 4 전환 계획 작성
4. 기존 기능과 신규 기능 매핑
5. Phase 1만 구현
6. 실행/오류 확인
7. 성공하면 Phase 2 진행
```

처음부터 전체 게임을 생성하지 않는다.

**Phase 1 → 테스트 → Phase 2 → 테스트 방식으로 진행한다.**

그리고 각 단계에서 실제 실행 가능한 결과를 유지한다.
